# 전문 모듈 A · 인증우회

## 목표

허용된 자체 로컬 웹 실습 문제 하나를 입력부터 **Oracle의 외부 증거 판정**과 **Reporter 로그 저장**까지 처리하는 L1이 필수 목표다. 이 문서는 목표와 작업 경계를 설명하며 L1 구현·실행 완료를 주장하지 않는다.

`A파트 진행` 또는 `인증우회 작업`으로 시작하면 [A 규칙](AGENTS.md)을 읽고 [공통 계약](../00_공통/PROJECT_SPEC.md), [공개 역할표](../00_공통/개발_역할표.md), [협업 규칙](../00_공통/CODEX_개발협업.md), 현재 브랜치·PR·task-id/수정 경로가 맞는 [자기 인계](../91_개발작업기록/README.md)과 Git 상태를 확인한다.

## 입력·출력

- **입력:** Dispatcher가 `selected_module: A`로 선택한 v1 봉투. 허용 `target_id`, 관찰, 도구, 이전 결과와 실행 한도를 확인한다.
- **출력:** `producer: A`와 공통 필수 필드의 행동·관찰·증거 후보·오류·다음 행동. 중간 `status`는 미실행 `NOT_RUN` 또는 실행 후 Oracle 전 `UNKNOWN`이다.
- **최종:** Oracle가 외부 증거와 실행 여부로 상태를 한 번 판정하고 Reporter가 보존한다. A의 성공 주장만으로 `PASS`를 쓰지 않는다.

필드와 상태 의미, 허용 대상·요청 한도는 [PROJECT_SPEC](../00_공통/PROJECT_SPEC.md)가 기준이다. 계약 변경은 영향과 검증 계획을 적은 PR에서 검토받는다.

두 구성원은 제공된 계획서나 기존 프로토타입을 Codex와 비교해 도입·부분 도입·새 작성·보류를 결정한다. 결정 근거와 실제 자체 테스트를 작업 기록·PR에 남긴다. 별도 검토·내부 승인을 둘지는 팀이 선택한다. 다른 팀과 맞닿는 인터페이스는 영향받는 팀과 조율하며, 공통 계약·판정 책임·허용 범위 정책과 필수 시작/기록/변경 보존의 변경·생략은 [공통 예외 표](../00_공통/CODEX_개발협업.md)를 따른다.

## 이 폴더에서 발전시킬 파일

- `AGENTS.md`: Codex 작업 경계
- `MODULE_SPEC.md`: 역할·입력·출력·설계 이유
- `prompt.md`: 실제 모듈이 사용할 실행용 프롬프트
- `sample_io.json`: v1 mock 샘플
- `QA.md`: 재실행 명령·입력·기대값·실제값·근거

아직 없는 파일은 작업이 시작될 때 만든다. 먼저 공통 mock 검사와 A→Oracle 연결을 확인하고, 랩이 등록·초기화·제한된 뒤에만 실제 인증우회 L1을 검증한다. 실행이 없으면 `SKIP`과 이유를 [작업 기록](../91_개발작업기록/README.md)에 남긴다. 별도 검토를 수행한 경우 그 결과를, 그렇지 않으면 실제 테스트와 남은 검증을 PR에 적어 인계한다.

## 작업 연결

[최신 확인](../00_공통/작업시작_최신확인.md) 후 자기 브랜치·PR·task-id의 기록을 이어받는다. 팀의 가장 최근 날짜 기록은 자기 작업으로 간주하지 않는다. 같은 작업의 미완료 변경은 보존해 계속하고 겹치는 PR은 팀이 조율한다. 현재 설계는 팀 문서에, 실제 시도·아이디어 상태·검증은 자기 기록에 남긴다. 짝 검토는 의무가 아니며 일반 PR 병합 담당·방법은 팀이 선택한다. Oracle는 프로그램의 최종 판정 책임이며 사람의 매 실행 승인 대기열을 뜻하지 않는다. 로컬 검사 통과 뒤 자기 자료의 안전한 읽기 검토는 가능하지만 업로드 미완료를 준비 완료로 표시하지 않는다.

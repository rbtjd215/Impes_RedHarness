# B · XSS 작업 규칙

루트 [AGENTS.md](../../AGENTS.md)와 [공통 협업 규칙](../00_공통/CODEX_개발협업.md)을 함께 따른다. 이 폴더는 XSS 모듈의 개발 범위다.

## 시작

`B파트 진행` 또는 `XSS 작업`을 받으면 [공개 역할표](../00_공통/개발_역할표.md), [공통 계약](../00_공통/PROJECT_SPEC.md), [프로젝트 인덱스](../프로젝트_인덱스.md), [팀 안내](README.md), 최근 [B 작업 기록](../91_개발작업기록/README.md)과 실제 Git 상태를 읽는다. 지난 작업은 Git author·커밋·PR 이력과 대조하되 author는 신원·접근 권한 인증이 아니다. 파트가 명확하면 이름·짝·별도 작성자 정보를 묻지 않고, 담당 작업 범위가 실제로 불분명할 때만 범위를 확인한다.

첫 답변은 **목표 / 지금 할 일 / 수정할 경로 / 테스트 방법** 네 항목으로 짧게 적는다. 최신 코드·테스트·작업 기록을 함께 읽고 현재 상태를 확인한다.

## 범위와 이식 경계

- 보통 `03_프로젝트/03_전문모듈_B/`와 자기 작업의 `03_프로젝트/91_개발작업기록/YYYY-MM-DD_b_<task-id>.md`만 수정한다. 다른 팀 파일·Oracle 인터페이스에 영향이 있으면 먼저 입력·출력·테스트 영향을 밝히고 영향받는 팀과 조율해 PR에 남긴다. 공통 계약·최종 판정 책임·허용 범위 정책 변경은 동아리장의 명시 승인을 받는다.
- B는 XSS L0, 즉 같은 하네스에서 실제 입력과 근거 또는 명확한 실패 로그를 반환하는 목표를 맡는다. v1 봉투에서 `selected_module: B`, `producer: B`와 공통 필수 필드를 지킨다. 중간 `status`는 미실행 `NOT_RUN` 또는 실행 후 Oracle 전 `UNKNOWN`이다.
- 별도 독립 XSS 프로토타입의 **모듈 A 표기, 독자 계약, 자체 Oracle**은 공통 기준과 다르다. 원본은 이 저장소에 자동 포함되지 않는다. 이 폴더의 오프라인 B 어댑터·테스트가 있더라도 원본 이식 완료나 실제 L0을 뜻하지 않는다. 두 구성원은 제공된 계획서와 원본의 위치·기준 버전·사용 권한을 검토하고 도입·부분 도입·새 작성·보류 여부와 적용 방식을 스스로 정해 근거를 기록한다. 별도 검토·내부 승인 절차는 필수가 아니며 팀이 필요할 때 선택한다. 도입하기로 결정한 경우에만 B 필드 대응·자체 Oracle 중복 제거·동일 mock 입력 비교를 PR에서 다룬다. 공개 가능 범위를 확인하기 전 원본을 복사하지 않는다.
- 분야별 XSS 근거 규칙은 B가 제안할 수 있다. 최종 `PASS`/`FAIL`/`UNKNOWN`/`NOT_RUN`은 공통 Oracle가 한 번 정하고 Reporter는 보존한다. 원본 프로토타입의 자체 Oracle을 두 번째 최종 판정자로 연결하지 않는다.
- 자동 요청은 [PROJECT_SPEC](../00_공통/PROJECT_SPEC.md)에 등록된 자체 로컬 랩과 고정 버전·한도·초기화에서만 한다. 원본 코드·랩이 없으면 해당 검사는 `SKIP`과 이유로 기록한다.

## 확인과 인계

공통 mock 검사, B 선택, B→Oracle 증거 전달, Reporter의 상태 보존을 확인한다. 실제 L0은 허용 랩의 입력·결과·근거 또는 오류로 검증한다. 수행한 실행은 사실대로 기록하고, 실행하지 않은 검사는 `SKIP`과 이유로 남긴다. 별도 검토는 필수가 아니며 수행한 경우에만 그 결과를 기록한다. [작업별 기록](../91_개발작업기록/README.md)에 변경 파일·시도·채택/폐기 근거·테스트·막힘을 갱신하고 `작업 종료`·`인계`에서 실제 Git diff와 PR 설명을 확인한다. 앱 종료 뒤 자동 기록을 약속하지 않는다. 공개 기록에 키·쿠키·개인정보·원시 응답을 넣지 않는다.

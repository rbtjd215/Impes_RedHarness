# 전문 모듈 B · XSS

## 목표와 프로토타입 정렬

같은 하네스에서 XSS 모듈이 실제 입력을 받아 **근거 또는 명확한 실패 로그를 반환하는 L0**가 필수 목표다. L1은 확장 목표다. 별도 독립 XSS 프로토타입은 이 저장소에 그대로 들어 있지 않다. 이 폴더에 mock 전용 B 어댑터가 생겨도 실제 프로토타입 이식·로컬 랩 실행·L0 완료를 의미하지 않는다. 현재 상태는 Git·QA·작업 기록으로 확인한다.

`B파트 진행` 또는 `XSS 작업`으로 시작하면 [B 규칙](AGENTS.md), [공통 계약](../00_공통/PROJECT_SPEC.md), [공개 역할표](../00_공통/개발_역할표.md), [협업 규칙](../00_공통/CODEX_개발협업.md), 최근 [작업 기록](../91_개발작업기록/README.md)을 읽는다.

## 기존 원본을 검토할 때

원본은 독립 실행 가능하다고 보고됐지만 **모듈 A 표기, 독자 입력·출력 계약, 자체 Oracle**이 현재 팀 기준과 다르다. B팀의 두 구성원이 제공된 계획서·원본을 검토해 **도입·부분 도입·새 작성·보류** 중 하나와 적용 방식을 스스로 결정한다. 별도 검토·내부 승인을 둘지는 팀이 선택한다. 원본의 `runs/`, 설정, 원시 요청·응답과 내부 계획 문서를 통째로 복사하지 않는다. 도입을 선택한 경우에만 아래 항목을 PR에서 확인한다.

1. 원본 위치·기준 버전·사용 권한과 선택한 파일만 밝힌다.
2. XSS의 `selected_module`·`producer`를 `B`로 맞추고 독자 필드를 [공통 v1 봉투](../00_공통/PROJECT_SPEC.md)에 대응시킨다.
3. XSS 증거 추출·분야 규칙과 **최종 판정**을 분리한다. 최종 상태는 Oracle 한 곳에서 내리고 Reporter가 그대로 기록한다.
4. 같은 mock 입력의 전후 결과를 비교한다. 실제 L0은 허용 목록의 자체 로컬 랩에서 별도로 검증한다.

## 입력·출력과 파일

Dispatcher가 `selected_module: B`로 선택한 v1 입력, 허용 `target_id`, 관찰·도구·실행 한도를 받는다. `producer: B`와 행동·관찰·증거 후보·오류·다음 행동을 반환한다. 중간 `status`는 실행 전 `NOT_RUN`, 실행 후 Oracle 판정 전 `UNKNOWN`이다. B의 성공 주장은 최종 상태가 아니다.

`AGENTS.md`는 개발 규칙, `MODULE_SPEC.md`는 설계 경계, `prompt.md`는 실행용 프롬프트, `sample_io.json`은 mock 예시, `QA.md`는 재현 결과를 적는 자리다. 파일·코드가 실제로 없으면 있는 것처럼 쓰지 않는다. 계약 mock과 어댑터 테스트를 실행하되 원본 미이식·로컬 랩 미설정 검사는 `SKIP`과 이유를 기록한다. 도입 결정 근거와 실제 테스트를 작업 기록·PR에 적고, 별도 검토를 수행했다면 그 결과도 적어 인계한다.

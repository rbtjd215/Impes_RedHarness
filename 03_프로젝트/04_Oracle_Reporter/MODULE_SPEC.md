# Oracle·Reporter — минимальная спецификация

Это спецификация локального офлайн-прототипа. Его реализация и синтетические
проверки описаны в [QA.md](QA.md); реальная лаборатория и интеграция не проверены.
Основа — [общий контракт](../00_공통/PROJECT_SPEC.md) и [руководство команды](README.md).
Общий контракт имеет приоритет; его поля и значения здесь не переопределяются.

## Цель и границы первого шага

На синтетических данных показать, как Oracle получает наблюдения A/B, проверяет
критерий и выносит единственный окончательный статус, а Reporter сохраняет этот
статус, доказательства и предыдущие конверты без изменений.

Первый прототип использует только `offline_mock`. Синтетическое доказательство
демонстрирует обработку данных и не подтверждает реальную уязвимость. Запросы к
стенду можно добавлять только после определения разрешённого локального адреса,
версии, сброса и лимитов. В текущем общем контракте эти параметры ещё не заданы.

## Формат данных

Каждый этап создаёт отдельный JSON-конверт со всеми полями v1:

| Поле | Требование |
|---|---|
| `contract_version` | Строка `1.0` |
| `run_id`, `target_id` | Идентификаторы одного выполнения и цели |
| `selected_module` | `A` или `B`; сохраняется во всех этапах |
| `producer` | Создавший конверт этап: `DISPATCHER`, выбранный `A`/`B`, `ORACLE`, `REPORTER` |
| `observation` | Объект наблюдений; для complete-v1 содержит `execution_mode` |
| `actions` | Массив действий; при отсутствии действий — `[]` |
| `status` | `PASS`, `FAIL`, `UNKNOWN` или `NOT_RUN` по правилам этапа |
| `evidence` | Массив доказательств; при отсутствии — `[]` |
| `error` | `null`, безопасная строка или объект ошибки |
| `next_action` | Строка с дальнейшим действием |

В полном выполнении сохраняются ровно четыре конверта:
`DISPATCHER → A или B → ORACLE → REPORTER`. Версия, идентификаторы, выбранный модуль
и режим выполнения согласованы. Повторная попытка получает отдельный `run_id`.

Элемент `actions` содержит непустые `kind`, `source`, `summary`. Проверка Oracle
имеет `kind: verify` и `criterion_id`. Элемент `evidence` содержит непустые `kind`,
`source`, `criterion_id`, `summary` или `evidence_ref`, а также `execution_mode`,
совпадающий с режимом конверта.

## Oracle: вход, выход и решение

**Вход:** конверт выбранного A/B, критерий проверки для соответствующего
`target_id` и доступные проверяемые наблюдения. Для первого прототипа критерии и
наблюдения синтетические. Функция `offline_oracle.decide(specialist, criterion,
check=None)` получает их как аргументы; это не новые обязательные поля общего
JSON-контракта. Их формат описан в [правилах](판정규칙.md).

Перед решением проверяются структура, идентификаторы и источник наблюдений.
Некорректный вход отклоняется с диагностикой как ошибка интерфейса; его нельзя
превращать в продуктовый `FAIL`. Функция выдаёт безопасный `InputError`.

**Выход:** новый конверт `producer: ORACLE`. Oracle сохраняет идентификаторы,
фиксирует собственные действия проверки и единственный окончательный статус.
Входной конверт не изменяется. A/B передают только `UNKNOWN` после действий или
`NOT_RUN` при отсутствии выполнения; их заявление об успехе не заменяет проверку.

| Итоговый статус | Основание |
|---|---|
| `PASS` | Проверяемое доказательство выполнения критерия успеха |
| `FAIL` | Подтверждённое выполнение и проверяемое доказательство неуспеха по критерию |
| `UNKNOWN` | Действия A/B или Oracle были, но доказательств для решения недостаточно |
| `NOT_RUN` | Нет действий выполнения A/B и Oracle и нет итоговых доказательств |

Для `PASS`/`FAIL` массив итоговых доказательств непустой и состоит из
`kind: verification`. Каждое доказательство связано через `criterion_id` с
действием `verify` Oracle и дополнительно содержит:

- `result: matched` для `PASS` или `not_matched` для `FAIL`;
- `execution_basis: specialist_execution`, если A/B выполнил действия, его статус
  `UNKNOWN` и `actions` непустой;
- либо `execution_basis: independent_check`, если Oracle самостоятельно проверил
  основание. В этом случае A/B может иметь `NOT_RUN`.

Oracle формирует `verification` после проверки наблюдения, а не доверяет готовому
`result` из входа. Отсутствие маркера, исключение инструмента или слова «успех»
сами по себе не обосновывают `PASS`/`FAIL`. При неполной проверке после действий
нужен `UNKNOWN`; при полном отсутствии выполнения — `NOT_RUN`. Конфликтующие
наблюдения в первом прототипе предлагается оставлять `UNKNOWN` с объяснением.
Доменная логика критериев A/B требует отдельного согласования с этими командами.

## Reporter: вход, выход и сохранение

**Вход:** упорядоченные конверты Dispatcher, выбранного A/B и Oracle одного
выполнения и локальное место сохранения. Путь хранения — параметр реализации,
а не обязательное поле общего конверта.

**Выход:** новый конверт `producer: REPORTER`, сохраняющий Oracle `status` и
`evidence` без изменений. Собственные `observation`, `actions`, `error`,
`next_action` описывают запись. Reporter не переоценивает результат Oracle.

Хранение первого прототипа — JSON-массив из четырёх конвертов в
временном каталоге теста. Reporter работает с копиями входов. При успешной
записи файл повторно читается: проверяются complete-v1, порядок, сохранность
трёх предыдущих конвертов и равенство статуса/доказательств Oracle и Reporter.
Заявлять успех хранения можно только после записи и успешного повторного чтения.
`offline_reporter.store(records, path)` принимает первые три конверта; возвращает
объект с `storage: written_and_verified` и REPORTER. Запись использует новый файл
без перезаписи существующего; атомарная запись и восстановление пока не реализованы.

При ошибке записи, чтения или проверки сохранённого содержимого Reporter
возвращает диагностический конверт, сохраняя Oracle `status`/`evidence`:

- `observation.storage: failed`;
- `error` — объект с `kind: storage_error` и безопасным описанием;
- `next_action` — предложение исправить хранение и повторить сохранение.

Такой результат не доказывает, что файл сохранён. Например, Oracle `PASS` и ошибка
Reporter совместимы: успешность выполнения и успешность хранения — разные факты.
Запись Reporter не считается действием выполнения цели и не меняет `NOT_RUN`.
Форматная проверка не доказывает истинность доказательств или факт записи на диск.

## Таблица проверочных случаев

Все группы случаев ниже проверены тестами локального офлайн-прототипа; соответствие
случаев и фактических проверок указано в QA.md. Полные успешные потоки проверены
для обоих значений `selected_module`. Это не реальные A/B-модули.

| ID | Синтетический вход или условие | Ожидаемое поведение |
|---|---|---|
| OR-01 | A/B выполнил действие; Oracle подтвердил критерий успеха | `PASS`; verification/matched, specialist_execution, связь с verify |
| OR-02 | Выполнение подтверждено; Oracle проверил критерий неуспеха | `FAIL`; verification/not_matched, specialist_execution, связь с verify |
| OR-03 | Действия были, наблюдение неполно | `UNKNOWN`; нет выдуманных окончательных доказательств |
| OR-04 | Нет действий A/B и Oracle, итоговых доказательств нет | `NOT_RUN`; запись Reporter его не меняет |
| OR-05 | После действия A/B сообщает «успех», проверяемого наблюдения нет | `UNKNOWN`, а не `PASS` |
| OR-06 | Инструмент дал ошибку после попытки либо маркер просто отсутствует | `UNKNOWN`, пока не доказан критерий неуспеха; не автоматический `FAIL` |
| OR-07 | A/B `NOT_RUN`, Oracle независимо проверил критерий успеха | `PASS` с independent_check и собственным verify; допустимо по контракту |
| OR-08 | A/B `NOT_RUN`, Oracle независимо проверил критерий неуспеха | `FAIL` с independent_check и собственным verify; допустимо по контракту |
| OR-09 | Нет обязательного поля, идентификаторы расходятся либо A/B прислал окончательный PASS/FAIL | Вход отклонён диагностикой; продуктовый `FAIL` не создаётся |
| RP-01 | Четыре корректных состояния по отдельности; обычная запись | Повторное чтение успешно; четыре конверта в порядке; входы, status/evidence сохранены |
| RP-02 | Ошибка записи после Oracle `PASS` | Статус остаётся `PASS`, evidence сохранён; storage failed и storage_error; хранения успех не заявлен |
| RP-03 | Файл не читается либо содержимое изменено перед повторной проверкой | Ошибка хранения, сохранность не подтверждена; решение Oracle не меняется |
| CT-01 | Полный поток: пропущен/повторён этап, смешаны execution_mode или изменены evidence Reporter | Проверка complete-v1 отклоняет поток |

## Проверка и следующие задачи

Существующие общие mock использовались как справочный материал. Командная
реализация имеет отдельную демонстрацию:

```powershell
python -B tools/run_checks.py
python -B "03_프로젝트/04_Oracle_Reporter/run_offline.py"
```

Команды выполняются из корня репозитория на Python 3.12+. В текущем окружении
`python`/`py` отсутствуют в PATH: для запуска используется полный путь к
доступному встроенному Python. Текущий запуск зафиксирован в
[журнале прототипа](../91_개발작업기록/2026-10-26_oracle_offline-prototype-1026.md).

Созданы правила, compact fixtures в `sample_io.json`, Oracle, Reporter, CLI и тесты.
Группа `oracle` автоматически выполняется существующим общим runner. Дальше нужно
согласовать реальные критерии с A/B и интерфейс подключения с интеграцией; вопросы
разрешённого стенда решаются до реальных запросов. Финальная командная фиксация
проекта и реальная интеграция не заявлены.

Публичные примеры содержат только синтетические идентификаторы и безопасные
сводки. Ключи, cookies, персональные данные, сырые ответы и приватные пути в них
не помещаются. Итоговый учебный отчёт третьей недели хранится отдельно от
публичного репозитория.

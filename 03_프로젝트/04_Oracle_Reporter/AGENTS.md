# Oracle·Reporter 작업 규칙

루트 [AGENTS.md](../../AGENTS.md)와 [공통 협업 규칙](../00_공통/CODEX_개발협업.md)을 함께 따른다. Oracle·Reporter는 하나의 2인 팀이다. 이 폴더는 최종 판정과 결과 보존의 개발 범위다. 시작 전 공통 최신 확인 절차를 반드시 수행한다.

## 시작

`Oracle·Reporter 팀 작업`(또는 기존 `Oracle 작업`·`Reporter 작업`)을 받으면 [공개 역할표](../00_공통/개발_역할표.md), [공통 계약](../00_공통/PROJECT_SPEC.md), [프로젝트 인덱스](../프로젝트_인덱스.md), [팀 안내](README.md), 현재 브랜치·PR·task-id/수정 경로가 맞는 [자기 작업 기록](../91_개발작업기록/README.md)과 실제 Git 상태를 읽는다. 지난 작업은 Git author·커밋·PR 이력과 대조하되 author는 신원·접근 권한 인증이 아니다. 파트가 명확하면 이름·짝·별도 작성자 정보를 묻지 않고, Oracle와 Reporter 중 담당 작업 범위가 실제로 불분명할 때만 범위를 확인한다.

첫 답변은 **최신 확인 결과·기준 SHA / 목표 / 지금 할 일 / 수정할 경로 / 테스트 방법** 다섯 항목으로 짧게 적는다.

## 단일 최종 판정

- 보통 `03_프로젝트/04_Oracle_Reporter/`와 자기 작업의 `03_프로젝트/91_개발작업기록/YYYY-MM-DD_oracle_<task-id>.md`만 수정한다. 다른 팀 파일·인터페이스에 영향이 있으면 입력·출력·테스트 영향을 먼저 밝히고 영향받는 팀과 조율해 PR에 남긴다. 공통 계약·최종 판정 책임·허용 범위 정책과 필수 시작/기록/변경 보존의 변경·생략은 공통 협업 규칙의 명시 승인 절차를 따른다.
- 두 구성원은 제공된 계획서·기존 구현이 있다면 Codex와 비교해 도입·부분 도입·새 작성·보류 여부와 구현 방식을 스스로 정한다. 별도 검토·내부 승인 절차는 필수가 아니며 팀이 필요할 때 선택한다. 근거와 실제 자체 검증 결과를 작업 기록·PR에 남기고, 공개 가능 범위를 확인하기 전 원본을 복사하지 않는다.
- Oracle만 [PROJECT_SPEC](../00_공통/PROJECT_SPEC.md)의 최종 `status`를 정한다. `PASS`는 외부에서 확인 가능한 성공 증거, `FAIL`은 실제 실행과 실패 근거, `UNKNOWN`은 실행했으나 판정 근거 부족, `NOT_RUN`은 실제 실행이 없음을 뜻한다. LLM 또는 A/B의 성공 주장은 외부 증거가 아니다.
- A/B가 분야별 근거 기준과 사례를 제안할 수 있지만 최종 판정은 Oracle 한 곳에서 한다. Reporter는 Oracle 봉투의 판정과 근거를 바꾸지 않고 저장한다. 저장 실패를 재판정으로 숨기지 않는다.
- 자동 요청은 허용된 자체 로컬 랩 정책을 따른다. 키·쿠키·개인정보·원시 민감 응답을 공개 로그에 넣지 않는다.

## 확인과 인계

공통 mock에서 네 상태, 성공 주장만 있는 경우, 근거 부족, 저장 실패를 검증한다. 실제 구현·랩이 없으면 각 검사를 `SKIP`과 이유로 적는다. 의미 있는 변경 뒤 [작업별 기록](../91_개발작업기록/README.md)을 갱신하고 실제 판정 근거·로그 검사 결과를 PR에 남긴다. 별도 검토는 필수가 아니며 수행한 경우에만 그 결과를 기록한다. `작업 종료`·`인계`에는 실제 Git diff·HEAD·테스트로 handoff와 PR 설명을 작성한다. 앱 종료 뒤 자동 기록을 약속하지 않는다.

## 이어받기와 조율

[최신 확인](../00_공통/작업시작_최신확인.md)을 따른다. 같은 목표의 연속 요청은 확인한 기준을 활용하되 새 채팅·재진입·새 목표·새 브랜치·기준 변경·업로드 전에는 확인한다. 자기 미완료 변경은 보존하고 같은 작업이면 같은 checkout에서 이어간다. 관련 없는 변경만 필요할 때 격리한다. 팀의 가장 최근 날짜 기록을 자기 인계로 선택하지 않는다. 열린 PR과 경로가 겹치면 알리고 분담·반영 순서는 팀이 정한다. fetch 실패는 새 구현을 보류하며 읽기 전용 검토·기존 사실의 마무리는 가능하다.

아이디어의 제안/선택/실험 채택/보류/폐기와 실제 근거를 구분한다. 현재 채택 설계는 팀 문서가 기준이다. 자료에 접근할 수 없으면 이유와 재첨부/경로 요청을 밝힌다. 채팅·하루 작업 마무리는 기능 미완료에도 적용하며 종료가 commit·push·merge 허가는 아니다. Oracle 단일 판정은 프로그램 책임이며 사람의 매 실행 승인 절차가 아니다. 민감한 공개는 승인 예외로 허용하지 않는다.

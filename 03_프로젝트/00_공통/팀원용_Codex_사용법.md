# 팀원용 Codex 사용법 · 한 페이지

**작업 장소:** 공개 공동 개발 저장소 [Impes_RedHarness](https://github.com/rbtjd215/Impes_RedHarness). GitHub에서 `Code` → HTTPS 주소를 복사해 로컬에 clone하고, Codex에서 그 폴더를 연다. 파일·브랜치·PR·기록은 누구나 볼 수 있으므로 개인 정보, 키, 쿠키, 내부 교안·운영 기록을 넣지 않는다. push 권한과 리뷰 담당은 팀장에게 확인한다.

## 시작

Codex에 파트를 알려 준다. Codex는 역할표·[`PROJECT_SPEC.md`](PROJECT_SPEC.md)·팀 안내·최근 `91_개발작업기록/`·Git 상태를 읽고 **목표 / 지금 할 일 / 수정 경로 / 테스트 방법**을 짧게 보여 준다. 파트가 명확하면 이름을 묻느라 멈추지 않는다. 이름 확인은 안내용이며 접근 권한 검증이 아니다.

```text
A파트 진행. 역할표·공통 계약·A팀 안내·최근 인계를 Git 상태와 대조해 목표, 수정할 경로, mock 테스트 방법을 알려줘.
```

```text
B파트 진행. XSS 팀 안내와 최근 인계를 읽고 지금 할 일, B팀 경로, 검증 방법을 알려줘.
```

`작업 시작`만 말해 실제 담당이 불분명하면 Codex가 파트만 확인한다. `XSS 작업`, `Oracle 작업`, `Reporter 작업`도 사용할 수 있다. 현재 파트는 **A=인증우회, B=XSS, 별도 Oracle·Reporter**다.

## 기능 요청과 기록

**기능, 예상 입력·출력, 수정 범위, 테스트**를 한 문장에 넣는다.

```text
A팀: 인증우회 mock 입력을 공통 계약 v1으로 처리해줘. A팀 경로만 수정하고 계약 검사와 QA 결과를 작업별 기록에 남겨줘.
```

```text
B팀: XSS 프로토타입 원본이 확인되면 A 표기를 B로 맞추고 자체 계약·Oracle과 공통 기준의 차이를 정리해줘. B 경로의 mock 테스트를 실행하고 최종 판정은 공통 Oracle 한 곳에 남겨줘.
```

의미 있는 편집·실행·실패 뒤에는 `03_프로젝트/91_개발작업기록/`에 **작업마다 별도 파일**을 갱신한다. 변경 파일, 실제 시도와 결과, 채택·폐기한 이유, 테스트 통과·실패·건너뜀, 막힌 점, 기준 커밋·PR, 다음 행동을 적는다. 전체 대화·숨은 추론·추측한 결정·개인정보·비밀은 적지 않는다. 허용 랩과 한도가 정해지기 전에는 실제 웹 요청 대신 mock만 쓴다.

## 종료와 PR

```text
작업 종료. 실제 Git 변경과 테스트를 확인해 내 작업 기록, 짧은 인계, PR 설명을 작성해줘.
```

다음에는 `지난 B팀 인계를 Git 상태와 대조해 이어서 진행해줘`처럼 시작한다. Codex 앱이 닫힌 뒤 자동 기록되지는 않는다. 작업 중 체크포인트와 명시적 종료·재진입으로 이어간다.

작업마다 최신 `main`에서 별도 브랜치(예: `codex/a-auth-mock`, `codex/b-xss-contract`)를 만들고 **자기 변경만** 커밋·push한다. PR에서는 `module-development.md`를 지정한다(`gh pr create --template module-development.md` 또는 GitHub PR URL의 `template=module-development.md`). 짝의 같은 입력 실행·검토 결과를 PR에 남긴 뒤 팀장이 계약 영향과 통합을 확인해 병합한다. 담당 외 파일·공통 계약을 바꿔야 하면 영향 범위와 테스트를 먼저 설명하고 PR 검토를 받는다. `AGENTS.md`·`CODEOWNERS`는 폴더별 접근·수정 권한을 강제하지 않는다.

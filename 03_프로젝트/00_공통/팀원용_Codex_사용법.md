# 팀원용 Codex 사용법 · 한 페이지

작업 장소는 공개 [Impes_RedHarness](https://github.com/rbtjd215/Impes_RedHarness)다. **A=인증우회, B=XSS, Oracle·Reporter=2인 한 팀**이다. 각자 clone하고 실제 저장소 폴더를 Codex 프로젝트로 연다. 브랜치·PR·기록도 공개되므로 비밀값·개인정보·원시 출력·내부 자료를 넣지 않는다. 현재 저장소 파일·원격 SHA·PR/main 상태로 실제 규칙의 적용을 확인한다.

## 1. 처음 준비

```powershell
git clone https://github.com/rbtjd215/Impes_RedHarness.git
cd Impes_RedHarness
```

복제한 `Impes_RedHarness` 폴더를 Codex 프로젝트로 연결한다. 준비 폴더에서 복제했다면 새 저장소 폴더로 다시 연결한다. 작성자 설정은 업로드 전에 본인이 로컬에서 확인하며 실제 이름·이메일을 기록/채팅에 붙이지 않는다. 필요하면 본인이 확인한 공개 표시 이름·정확한 GitHub Settings → Emails의 noreply 주소를 직접 로컬 설정하거나 적용만 명시 위임한다. 다른 사람·전역 설정 변경과 값 추측은 금지한다. [GitHub 공식 안내](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)

```text
A파트 진행. 환경 준비 로컬 검사를 확인해 주세요. 기존 변경을 보존하고 원격 최신 확인 후 현재 규칙·팀 안내와 검증 README의 필수 검사를 실행해 주세요. 자기 작업별 기록을 작성하고 로컬 검사·기록 업로드·PR 상태를 나누어 먼저 보여 주세요. 아직 commit·push하지 말아 주세요.
```

작성자 값을 아직 몰라도 도구·루트·규칙·필수 검사로 로컬 준비를 확인하고 안전한 계획/설계 읽기 검토를 이어갈 수 있다. 본인 작성자 확인은 업로드 전에 마친다.

B팀은 `B파트 진행`, Oracle·Reporter 팀은 `Oracle·Reporter 팀 작업`으로 바꾼다. [환경 준비 절차](환경준비_완료확인.md)를 따른다. 로컬 검사 통과 뒤 자기 계획서/구현물의 안전한 읽기 검토를 제안받을 수 있다. 원격 업로드·PR 미완료는 별도로 표시한다. 이미 제공한 자료는 반복 요청하지 않는다.

## 2. 환경 구축 후 작업·새 채팅의 시작

```text
A파트 진행. 원격 최신 상태와 저장소 규칙을 확인하고 현재 브랜치·PR·task-id의 인계를 Git 상태와 대조해 주세요. 인증우회 모듈의 목표·할 일·수정 경로·테스트를 짧게 알려 주세요.
```

```text
B파트 진행. XSS 팀의 현재 설계와 제 브랜치의 인계를 읽고 이어서 진행해 주세요. 자기 미완료 변경은 보존하고 겹치는 열린 PR이 있으면 알려 주세요.
```

새 채팅·재진입·새 목표·새 브랜치는 [최신 확인](작업시작_최신확인.md)을 먼저 수행한다. 같은 목표의 연속 요청마다 긴 시작 문구를 반복할 필요는 없다. 기준 변경·오래 중단 후 재개·업로드 전에는 다시 확인한다. fetch 실패는 새 구현을 보류하지만 읽기/진단·기존 사실의 마무리는 가능하다. 같은 팀의 최신 날짜 기록이 내 작업은 아니며 현재 브랜치→PR→task-id/경로가 맞는 기록을 이어받는다.

기능 요청은 목표·예상 입력/출력·수정 범위·완료 조건을 적는다. 예: `A팀 경로에서 인증우회 mock을 공통 계약으로 처리해 주세요. 실제 테스트와 막힌 점을 기록해 주세요.` / `B팀 기존 XSS 구현을 읽고 도입 후보·공통 계약 차이·Oracle 중복을 검토해 주세요. 공개 가능한 파일과 최소 검증을 제안해 주세요.` 실제 채택·분업·내부 검토는 팀이 정한다. Oracle 판정은 프로그램 책임이며 팀원의 매 실행 승인을 요구하지 않는다.

## 3. 채팅·하루 마무리와 아이디어

```text
오늘 작업은 여기까지 하겠습니다. 기능이 미완료여도 실제 Git 변경과 테스트·막힘·다음 할 일을 확인해 자기 작업 기록, 짧은 인계와 PR 설명을 작성해 주세요. 아이디어는 제안·선택·실험 채택·보류·폐기를 구분하고 확인된 이유만 남겨 주세요. 아직 commit·push·merge하지 말아 주세요.
```

중간에는 `여기까지 체크포인트를 기록해 주세요.`로 정리한다. Codex가 `03_프로젝트/91_개발작업기록/`의 자기 파일을 작성하므로 양식을 직접 채울 필요는 없다. 기록 링크에서 변경·실제 방법/결과·검증 PASS/FAIL/SKIP·아이디어·다음 행동을 확인한다. 전체 대화·숨은 추론·추측한 결정·개인 작업량 순위는 기록하지 않는다. 앱을 닫은 뒤 자동 기록되지는 않는다.

## 4. 결과 확인 후 업로드·PR

```text
공개할 diff와 자기 기록을 검토하고 원격 최신 상태를 다시 확인해 주세요. 이번 변경의 정확한 파일만 제 작업 브랜치에 commit·push해 PR을 만들어 주세요. 원격 브랜치 SHA·파일·PR head를 확인하고 로컬·업로드·PR 상태를 나누어 알려 주세요.
```

팀이 일반 PR의 내부 검토·병합 담당/방법을 정한다. 모든 PR에 짝 검토·동아리장 승인은 필요하지 않다. 다른 팀 영향은 당사자와 조율하고 [공통 예외 표](CODEX_개발협업.md)의 변경/생략만 동아리장 명시 승인을 받는다. 민감한 공개는 예외 허용하지 않는다. Git author/committer·SHA·PR로 변경을 추적하며 이는 신원 인증이 아니다. AGENTS.md·CODEOWNERS는 폴더 권한 장치가 아니며 실제 권한·CI/보호 적용을 별도 확인한다.

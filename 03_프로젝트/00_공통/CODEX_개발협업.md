# RedHarness 모듈 개발 협업 규칙

이 저장소는 공개다. 공개 가능한 계약·규칙·mock·검토된 코드만 둔다. 내부 자료·원시 실행 결과·비밀값·개인정보를 가져오지 않는다. 자료 제공은 공개 commit 허가가 아니며 민감한 공개를 승인 예외로 허용하지 않는다.

## 시작과 재시작

`A파트 진행`·`인증우회 작업`은 A, `B파트 진행`·`XSS 작업`은 B, `Oracle·Reporter 팀 작업`(기존 `Oracle 작업`·`Reporter 작업`도 가능)은 한 팀으로 시작한다.

1. [최신 확인](작업시작_최신확인.md)을 따른다. 새 채팅·재진입·새 목표·새 브랜치에는 기존 변경 보존, fetch, main/upstream·공통 기준 대조를 파일 수정 전에 수행한다. 같은 목표의 연속 요청은 확인한 기준을 활용하되 기준 변경·오래 중단 후 재개·업로드 전에는 다시 확인한다.
2. 루트 AGENTS.md·README.md, 프로젝트 인덱스·역할표·PROJECT_SPEC.md·검증 안내와 팀 AGENTS.md·README.md·현재 설계를 읽는다. 이전 채팅 기억보다 확인된 현재 기준을 우선한다.
3. **현재 브랜치 → 연결 PR → task-id·수정 경로가 맞는 기록** 순으로 자기 인계를 찾는다. 같은 팀의 최신 날짜 기록은 참고로만 읽는다. 기록과 HEAD·diff·미추적 파일이 다르면 먼저 알린다. 자료에 접근할 수 없으면 이유와 재첨부/경로 요청을 밝힌다.
4. **최신 확인 결과·기준 SHA / 목표 / 할 일 / 수정 경로 / 테스트**를 짧게 알린다. 열린 PR과 수정 경로가 겹치면 경고하고 조율 방법은 팀이 정한다. 파트가 명확하면 바로 읽고 실제 불분명한 파트·작업 범위만 확인한다. 이름·짝을 별도 수집하지 않는다.

fetch 실패·미해결 공통 기준 차이·충돌은 새 개발 수정을 보류한다. 진단·읽기 전용 자료 검토·기존 사실의 종료 기록은 가능하나 새 구현을 오프라인으로 시작하지 않는다. 자기 미완료 변경은 같은 작업임을 확인하면 같은 checkout에서 이어간다. 관련 없는 변경만 필요할 때 별도 worktree로 격리하며 깨끗한 새 작업은 작업 브랜치로 시작할 수 있다. 자동 pull·stash·reset으로 변경을 숨기거나 덮지 않는다.

## 담당과 팀 자율

| 담당 | 기본 경로 | 목표 |
|---|---|---|
| A · 인증우회 | 03_프로젝트/02_전문모듈_A/ | 허용 로컬 문제 하나의 L1 |
| B · XSS | 03_프로젝트/03_전문모듈_B/ | 같은 하네스의 L0 |
| Oracle·Reporter · 2인 한 팀 | 03_프로젝트/04_Oracle_Reporter/ | 단일 최종 판정과 상태·근거 보존 |
| Dispatcher·통합 | 03_프로젝트/01_Dispatcher/, 03_프로젝트/05_통합/ | 회장 담당의 공통 연결·전체 재실행; 대행 미확인 |

팀은 계획·분업·구현 방법·내부 검토·프로토타입 채택·작은 작업 단위·일반 PR 병합 방법을 정한다. 모든 팀 PR에 짝 검토·팀장 승인을 요구하지 않는다. 다른 팀 파일·인터페이스에 영향이 있으면 범위·호환성·테스트를 해당 팀과 조율하고 PR에 남긴다. 겹친 경로는 분담·순차 반영·병합 순서 중 팀이 방법을 정한다. 현재 B mock은 참고이며 채택·실제 L0 완료가 아니다.

A/B는 공통 v1 봉투의 관찰·행동·근거 후보를 반환한다. Oracle 프로그램만 최종 상태를 한 번 판정하고 Reporter가 상태·근거를 보존한다. Oracle 팀원의 매 실행 수동 승인을 뜻하지 않는다. A/B는 분야별 근거·mock·테스트 대역으로 독립 개발할 수 있으나 대역을 실제 Oracle·L1 완료로 표시하지 않는다. 실대상 요청은 허용 로컬 랩·초기화·한도가 확정된 뒤에만 실행한다.

## 공통 변경·예외 표

| 변경 또는 상황 | 처리 |
|---|---|
| 팀 안의 계획·구현·분업·내부 검토·프로토타입 채택 | 팀 자율. 실제 선택과 검증을 기록한다. |
| 다른 팀 파일·인터페이스 영향, 공통 의미는 유지 | 영향받는 팀과 범위·테스트·반영 순서를 조율하고 PR에 남긴다. |
| 공통 필수 필드·상태 의미·판정 책임·자동 실행 허용 범위의 변경/예외 | 이유·영향·호환성·검증·되돌림을 제안 PR에 적고 동아리장의 명시 승인을 받는다. 승인 전 확정/실행하지 않는다. |
| 필수 시작 확인·작업 기록·기존 변경 보존 규칙의 생략/완화 | 공통 예외로 같은 명시 승인 절차를 따른다. 일반 기능 PR마다 승인받는 뜻은 아니다. |
| 오탈자·깨진 링크·공통 의미를 유지하는 설명 보완 | 일반 PR로 처리하며 공통 예외 승인을 요구하지 않는다. |
| 비밀값·개인정보·민감한 원시 로그·내부 자료 공개 | 공개하지 않는다. 동아리장 승인으로 예외 허용하지 않으며 공개 안전한 요약/선별 파일을 검토한다. |

기술 계약의 상세 기준은 PROJECT_SPEC.md다. 공통 규칙·계약 제안은 토론·검토 가능하지만 승인 전 공통 결정으로 표시하지 않는다. GitHub 권한·보호 설정은 별도 실제 설정으로 확인하며 AGENTS.md·CODEOWNERS는 폴더 권한을 강제하지 않는다.

## Git·PR·병합

각자 자기 clone과 확인한 Git author/committer를 사용한다. 본인이 직접 설정하거나 본인이 확인한 공개 표시 이름·정확한 GitHub noreply 주소의 **저장소 로컬 적용을 명시 위임했을 때만** Codex가 적용한다. 이름·이메일 추측·다른 사람/전역 설정 변경은 금지하며 실제 값은 공개 기록·채팅에 출력하지 않는다. [GitHub 커밋 이메일 안내](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)를 따른다.

최신 확인 가능한 기준에서 작업별 `codex/` 브랜치와 PR을 사용한다. 자기 변경의 정확한 경로만 stage하고 `git add .`·강제 push·파괴적 reset을 사용하지 않는다. 종료 요청은 upload/merge 허가가 아니며 commit·push·PR/merge는 해당 사용자 요청 범위를 확인한다.

| PR 종류 | 책임과 확인 |
|---|---|
| 일반 팀 PR·환경 기록 | 팀이 실제 권한 안에서 병합 담당·방법·순서를 선택. 필수 인적 승인 없음. |
| 다른 팀 영향 | 해당 팀과 조율한 범위·검증을 기록. 고정 짝 승인으로 대체하지 않음. |
| 공통 예외 | 위 표의 동아리장 명시 승인 근거를 남김. |
| Dispatcher·전체 통합 | 기존 회장 배정. 대행은 미확인이며 자동 지정하지 않음. |

PR 설명은 목표·변경·검증·남은 위험·작업 기록 링크로 간결하게 작성하고 긴 기록을 복제하지 않는다. 준비 검사의 통과를 실제 모듈·전체 통합 성공으로 쓰지 않는다. 로컬/CI 결과와 실행하지 않은 검사를 구분한다. 자동 검사 파일과 GitHub의 required check/PR 보호는 별도다. 2026-10-01 확인 시 main 보호·required status checks·rulesets는 미적용이며 이번 로컬 문서로 설정되었다고 주장하지 않는다.

[로컬 CI 구성](../../.github/workflows/offline-checks.yml)의 workflow는 `RedHarness offline checks`, job은 `offline-checks`다. GitHub required-check의 실제 표시 이름은 업로드 후 실행 결과에서 확인해야 하며 아직 필수화하지 않았다. 설정을 검토할 때 일반 팀 PR에 사람의 고정 승인 수를 추가하지 않는다.

변경 추적은 author/committer·SHA·PR을 사용하며 신원·기여 비율 인증이 아니다. 미커밋 작성자는 추측하지 않는다. 상세 이력이 필요하면 팀이 일반 merge를 선택하거나 PR Commits를 확인한다. 커밋 수·줄 수를 개인 작업량 순위로 해석하지 않는다.

## 기록·종료·계획서 도입

첫 의미 있는 수정/테스트부터 자기 작업의 `91_개발작업기록/YYYY-MM-DD_<team>_<task-id>.md`를 만든다. 한 작업/브랜치에 한 파일과 주 작성자를 두며 날짜가 같아도 task-id를 고유하게 정한다. 다른 작업의 기록을 동시에 수정하지 않는다. 주요 결과·확정된 실패 원인·범위 변경·인계에 묶어 갱신한다.

아이디어는 **제안 / 선택 / 실험 채택 / 보류 / 폐기**를 구분하고 확인된 근거·검증 범위를 적는다. 제안은 미결정, 선택은 도입 방향 결정, 실험 채택은 확인한 범위에 한정한 사용, 보류는 남은 확인 대기, 폐기는 확인된 이유로 제외한 상태다. 계획과 실제 시도를 섞거나 폐기된 아이디어를 현재 결정으로 표시하지 않는다. 현재 채택 설계는 팀 안내·설계 문서에 반영하며 과거 기록은 필요한 범위만 연결한다. 전체 대화·숨은 추론·추측한 결정·비밀·개인정보·원시 실행 출력은 기록하지 않는다.

`오늘 작업은 여기까지`·`채팅 마무리`·`작업 종료`·`인계`는 기능 미완료에도 적용한다. 실제 status·HEAD·diff·미추적 파일·테스트 증거를 확인해 자기 기록과 짧은 handoff·PR 설명을 작성한다. 실행하지 않은 검사는 SKIP과 이유를 적고 오래된 테스트 결과는 기준 SHA·시점과 함께 표시한다. 앱을 닫은 뒤 자동 기록을 약속하지 않는다. 자기 최종 SHA를 기록에 넣으려 반복 commit하지 않고 원격 SHA·PR·완료 보고로 업로드를 확인한다.

처음 준비는 [환경 준비 완료 절차](환경준비_완료확인.md)를 따른다. 로컬 검사·기록 업로드·PR 상태를 따로 보고한다. 로컬 검사 통과 뒤 계획서/기존 구현물의 안전한 읽기 검토를 제안할 수 있으며 원격 실패를 준비 완료로 표시하지 않는다. 이미 자료가 있으면 재요청하지 않고, 접근이 안 될 때만 이유와 재첨부·경로 요청을 밝힌다. 실제 채택·수정 범위는 팀이 정하고 공통 예외는 위 표를 따른다.

# RedHarness 모듈 개발 협업 규칙

이 저장소는 공개다. 공개 가능한 계약·규칙·mock·검토된 코드만 둔다. 내부 운영 기록, 강사용 자료, 원시 실행 결과, 비밀 설정과 개인정보를 가져오지 않는다. 민감한 개발 내용이 필요하면 접근 권한이 확인된 별도 비공개 저장소에서 작업한다. 이 문서는 저장소 권한을 부여하지 않는다.

## 시작 문구와 읽을 자료

팀원이 Codex에 “작업 시작”, “A파트 진행”, “B파트 진행”, “XSS 작업”, “Oracle 작업”, “Reporter 작업”이라고 말하면 다음 순서로 처리한다.

1. 루트 AGENTS.md, README.md, 이 문서, 개발_역할표.md, PROJECT_SPEC.md, 검증/README.md를 읽는다.
2. A파트·인증우회는 03_프로젝트/02_전문모듈_A, B파트·XSS는 03_프로젝트/03_전문모듈_B, Oracle·Reporter는 03_프로젝트/04_Oracle_Reporter의 AGENTS.md와 README.md를 직접 읽는다. 루트에서 시작할 때 하위 AGENTS.md를 자동으로 읽었다고 가정하지 않는다.
3. 해당 파트의 최신 91_개발작업기록 인계를 읽고 브랜치·HEAD·기준 커밋·원격·PR·git status와 대조한다. fetch가 실패하면 로컬 원격 추적 정보만 확인했다고 밝힌다. 기존 수정 파일과 미추적 파일은 보존하고 이번 작업에 섞지 않는다.
4. 담당 목표, 지금 할 일, 수정할 경로, 실행할 테스트를 짧게 보여 준 뒤 작업한다. 인계와 Git 상태가 다르면 그 차이를 먼저 알린다.

파트가 명시됐으면 해당 자료를 곧바로 읽는다. “작업 시작”만으로 파트를 알 수 없고 기존 작업에서도 확인할 수 없을 때만 파트를 묻는다. 이름·짝·별도 작성자 정보를 묻거나 기록하지 않는다. GitHub 접근 권한은 실제 저장소 설정으로 확인하며 Git 커밋 메타데이터는 신원 인증이 아니다.

## 담당 경계와 공통 계약

| 담당 | 보통 수정하는 경로 | 목표 |
|---|---|---|
| A · 인증우회 | 03_프로젝트/02_전문모듈_A/ | 허가된 로컬 문제 하나의 L1 |
| B · XSS | 03_프로젝트/03_전문모듈_B/ | 같은 하네스에 연결되는 L0 결과 |
| Oracle·Reporter | 03_프로젝트/04_Oracle_Reporter/ | 외부 증거의 단일 최종 판정과 기록 |
| Dispatcher/통합 | 03_프로젝트/01_Dispatcher/, 03_프로젝트/05_통합/ | 모듈 선택·연결·전체 재실행 |

팀은 자기 파트의 계획, 구현 방법, 검토 방식, 프로토타입 채택·폐기와 작은 작업 단위를 자율적으로 정한다. B의 현재 오프라인 mock은 참고 자료이며 B팀의 채택 확정이나 실제 L0 완료가 아니다. 내부 시험을 위해 모든 단계에서 승인받을 필요는 없다. 팀 경계를 넘어 다른 팀의 파일·입출력에 영향이 있으면 해당 팀과 직접 조율하고 PR에 합의 범위와 검증 결과를 남긴다.

모든 모듈은 PROJECT_SPEC.md의 계약 버전 1.0 봉투를 따른다. A/B는 관찰·행동·근거 후보를 반환하며 최종 PASS/FAIL을 확정하지 않는다. Oracle이 최종 상태를 한 번 판정하고 Reporter는 상태·근거를 보존한다. mock 형식 검사는 00_공통/검증/에서 먼저 실행한다. 실대상 자동 요청은 계약의 로컬 랩 허용 목록·초기화·한도가 확정되기 전에는 하지 않는다.

**공통 필수 필드·상태 의미·최종 판정 책임·자동 실행 허용 범위**를 바꾸거나 예외를 두려면 수정 전 또는 제안 PR에서 실제 필요, 영향받는 팀, 호환성, 검증·되돌림 방법을 밝히고 동아리장의 **명시 승인**을 받는다. 영향받는 팀과도 조율한다. 일반 팀별 기능 PR, 내부 계획 변경, 프로토타입 선택에는 이 승인 절차를 적용하지 않는다. AGENTS.md와 CODEOWNERS는 작업 안내·검토 요청 수단이지 폴더별 읽기/수정 권한을 강제하지 않는다.

## Git, 기록, PR

1. 각 작업자는 저장소를 자기 환경에 clone하고 현재 Git author/committer 설정을 스스로 확인한다. 실제 값은 공개 기록이나 채팅에 붙여 넣지 않는다. 본인이 직접 설정하거나, 본인이 확인한 공개 표시 이름·GitHub noreply 주소의 **저장소 로컬 적용을 명시적으로 위임한 경우에만** Codex가 적용한다. 값을 추측하거나 다른 사람·전역 설정을 바꾸지 않는다. 정확한 noreply 주소는 각자 GitHub Settings → Emails에서 확인한다. [GitHub 공식 안내](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)를 따른다.
2. 최신 확인 가능한 기준에서 작업별 브랜치를 만들고 PR을 사용한다. codex/a-..., codex/b-..., codex/oracle-... 등 이름은 예시다. 기존 변경이 있으면 별도 체크아웃으로 격리하고 무차별 git add ., 다른 사람 파일 덮어쓰기, 강제 push를 피한다. 팀은 내부 작업·검토·병합 순서를 자율적으로 정한다.
3. 첫 의미 있는 수정이나 테스트부터 03_프로젝트/91_개발작업기록/YYYY-MM-DD_<team>_<task-id>.md를 만든다. 한 작업/브랜치에 한 파일을 두고 동시에 편집하지 않는다. 주요 결과, 확정된 실패 원인, 범위 변경, 인계 때 작은 편집을 묶어 갱신한다. 실제 Git 변경·실행한 테스트·막힘·다음 행동을 남긴다. 전체 대화·숨은 추론·추측한 결정·비밀·개인정보와 사람별 작업량 지표는 기록하지 않는다.
4. Git author는 설정된 작성자, committer는 커밋을 생성·적용한 사람이다. 각자 자기 변경을 커밋하고 커밋 SHA·PR로 추적한다. 둘 다 실제 편집자의 신원 인증은 아니므로 권한은 GitHub 설정으로 관리한다. 별도 이름·짝·작성자 칸을 만들지 않는다. 여러 사람의 커밋을 squash하면 상세 이력이 줄어드니 PR Commits를 확인하고 필요하면 일반 merge로 보존한다. 팀별 PR은 실제 검증과 남은 위험을 적고, 다른 팀 영향 또는 공통 계약 예외가 있을 때만 해당 조율·승인 근거를 덧붙인다.

## 작업 종료와 재시작

처음 환경을 준비한 팀원은 [환경 준비 완료 절차](환경준비_완료확인.md)에 따라 필수 mock·회귀 검사와 작업별 기록의 브랜치 업로드를 확인한다. 모두 확인되면 Codex가 본인의 계획서/구현물을 요청한다. 이미 제공된 자료는 최소 도입안 검토로 이어가고 팀이 채택 범위를 정한다. 같은 채팅에서 반복 요청하지 않는다.

“작업 종료”나 “인계”에는 실제 git status, HEAD·기준 커밋, 변경·미추적 파일, 테스트 결과를 확인한다. 자기 작업 기록을 갱신하고 목표·변경·검증·막힘·다음 행동의 짧은 인계와 PR 설명을 작성한다. 종료 메시지는 승인·병합·공개 배포를 뜻하지 않는다. 앱을 닫은 뒤 자동으로 기록된다고 약속하지 않는다.

다음 “작업 시작”에서는 최근 기록의 기준/종료 커밋·PR·변경 파일·테스트를 현재 Git 상태와 대조한다. 어긋난 부분을 먼저 알리고 필요한 테스트를 다시 실행한 뒤 이어간다. 기록이 없거나 불완전하면 실제 Git과 확인 가능한 테스트만 근거로 새 기록을 시작한다.

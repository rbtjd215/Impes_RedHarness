# RedHarness 모듈 개발 협업 규칙

이 저장소는 공개다. 공개 가능한 계약·규칙·mock·검토된 코드만 둔다. 내부 운영 기록, 강사용 자료, 원시 실행 결과, 비밀 설정과 개인정보를 가져오지 않는다. 민감한 개발 내용이 필요한 경우에는 접근 권한을 확인한 별도 비공개 저장소에서 작업한다. 이 문서는 저장소 권한을 부여하지 않는다.

## 시작 문구와 읽을 자료

팀원이 Codex에 “작업 시작”, “A파트 진행”, “B파트 진행”, “XSS 작업”, “Oracle 작업”, “Reporter 작업”이라고 말하면 다음 순서로 처리한다.

1. 루트 AGENTS.md, README.md, 이 문서, 개발_역할표.md, PROJECT_SPEC.md, 검증/README.md를 읽는다.
2. A파트·인증우회는 03_프로젝트/02_전문모듈_A, B파트·XSS는 03_프로젝트/03_전문모듈_B, Oracle·Reporter는 03_프로젝트/04_Oracle_Reporter의 AGENTS.md와 README.md를 직접 읽는다. 루트에서 시작할 때 하위 AGENTS.md를 자동으로 읽었다고 가정하지 않는다.
3. 해당 파트의 최신 91_개발작업기록 인계를 읽고 현재 브랜치·HEAD·기준 커밋·원격·PR·git status와 대조한다. fetch가 실패하면 로컬 원격 추적 정보만 확인했다고 밝힌다. 기존 수정 파일과 미추적 파일은 보존하고 이번 작업에 섞지 않는다.
4. 담당 목표, 지금 할 일, 수정할 경로, 실행할 테스트를 짧게 보여 준 뒤 작업한다. 인계와 Git 상태가 다르면 그 차이를 먼저 알린다.

파트가 명시됐으면 해당 자료를 곧바로 읽고 이름 확인 때문에 멈추지 않는다. “작업 시작”만으로 파트를 알 수 없고 역할표·기존 작업에서도 확인할 수 없을 때만 파트를 묻는다. 이름 확인은 안내와 작업 기록용이며 접근 권한 검증이 아니다. 실제 권한은 GitHub 저장소 설정으로 관리한다. 이름·짝 배정이 비어 있으면 임의로 채우지 않는다.

## 담당 경계와 계약

| 담당 | 보통 수정하는 경로 | 목표 |
|---|---|---|
| A · 인증우회 | 03_프로젝트/02_전문모듈_A/ | 허가된 로컬 문제 하나의 L1 |
| B · XSS | 03_프로젝트/03_전문모듈_B/ | 같은 하네스에 연결되는 L0 결과 |
| Oracle·Reporter | 03_프로젝트/04_Oracle_Reporter/ | 외부 증거의 단일 최종 판정과 기록 |
| 팀장 · Dispatcher/통합 | 03_프로젝트/01_Dispatcher/, 03_프로젝트/05_통합/ | 모듈 선택·연결·전체 재실행 |

모든 단계는 PROJECT_SPEC.md의 계약 버전 1.0 봉투를 사용한다. A/B는 관찰·행동·근거 후보를 반환하며 최종 PASS/FAIL을 확정하지 않는다. Oracle이 최종 상태를 한 번 판정하고 Reporter는 그 상태와 근거를 보존한다. mock 형식 검사는 00_공통/검증/에서 먼저 실행한다. 실대상 자동 요청은 계약의 로컬 랩 허용 목록과 초기화·한도가 확정되기 전에는 하지 않는다.

담당 밖 파일이나 공통 계약을 변경해야 하면 수정 전에 영향받는 경로·팀·입출력·호환성·검증 계획을 작업 기록과 PR에 적고 팀장 및 영향받는 팀의 검토를 요청한다. 공유 파일의 작성자는 한 번에 한 명으로 정한다. AGENTS.md와 CODEOWNERS는 안내와 리뷰 요청 수단이며 폴더별 읽기·수정 권한을 강제하지 않는다.

## 브랜치, 작업 기록, PR

1. 최신 확인 가능한 기준에서 작업마다 codex/a-..., codex/b-..., codex/oracle-..., codex/integration-...처럼 별도 브랜치를 만든다. 작업 전 원격 상태를 확인하고 기존 변경이 있으면 별도 체크아웃으로 격리한다. 다른 사람 파일 덮어쓰기, 무차별 git add ., 강제 push는 하지 않는다.
2. 첫 의미 있는 수정이나 테스트부터 03_프로젝트/91_개발작업기록/YYYY-MM-DD_<team>_<task-id>.md를 작성한다. 한 작업·브랜치에 한 파일과 한 명의 주 작성자를 둔다. 중요한 변경·검증·실패·방향 전환 때 체크포인트를 갱신한다. 공개 저장소에 남겨도 되는 요약만 기록하며 원시 실행 출력과 민감 정보는 제외한다.
3. 기능 요청은 목표·예상 입출력·담당 경로·완료 조건을 확인하고 구현한다. 실제 시도·관찰된 결과, 채택·폐기한 아이디어와 확인된 이유, 테스트 명령과 PASS/FAIL/SKIP, 막힌 점을 기록한다. 전체 대화·숨은 추론·추측한 결정은 기록하지 않는다.
4. 본인 변경 파일만 검토하고 개발 PR 템플릿을 사용한다. 짝은 같은 입력으로 실행하거나 변경을 검토해 PR에 남기고, 주 작성자가 자신의 기록에 반영한다. 팀장은 계약 영향·짝의 검증·범위·통합 테스트를 확인한 뒤 병합한다.

## 작업 종료와 재시작

“작업 종료”나 “인계”에는 실제 git status, HEAD·기준 커밋, 변경·미추적 파일과 실행한 테스트 결과를 확인한다. 본인 작업 기록을 갱신하고 목표·변경·검증·막힘·다음 행동의 짧은 인계 및 PR 설명을 작성한다. 종료 메시지는 승인·병합·공개 배포가 아니다. 앱이 닫힌 뒤 자동으로 기록된다고 약속하지 않는다.

다음 “작업 시작”에서는 최근 인계의 커밋·PR·파일·테스트를 현재 Git 상태와 비교한다. 차이가 있으면 먼저 보여 주고, 확인 가능한 상태에서 필요한 테스트를 다시 실행해 이어간다. 기록이 없거나 불완전하면 Git과 실제 테스트만 근거로 새 기록을 시작한다.

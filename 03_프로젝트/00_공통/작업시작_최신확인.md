# 개발 작업 시작 전 저장소 최신 확인

## 적용 시점

**새 채팅·작업 재진입·새 목표·새 브랜치**에는 파일 수정 전에 아래 전체 절차를 수행한다. 학생은 파트와 할 일만 말하면 되며 루트 AGENTS.md가 절차를 지정한다. 같은 목표의 연속 요청은 확인한 SHA·문서·시점을 활용한다. 원격/로컬 기준 변경, 다른 PR 반영, 오래 중단한 작업 재개, 업로드 전에는 다시 확인한다. 단순 상태 질문은 읽기 전용으로 답한다.

## 1. 기존 작업과 저장소 확인

현재 경로, Git 루트, 브랜치/HEAD, 수정·미추적·스테이징 파일, origin 주소, 진행 중인 merge/rebase를 확인한다. origin이 `rbtjd215/Impes_RedHarness`의 HTTPS/SSH 주소인지 확인한다. 다른 저장소라면 원격을 임의 변경하지 않고 올바른 프로젝트 경로를 안내한다. 자격 증명이 포함된 주소·개인 작성자 값을 공개 기록에 출력하지 않는다.

## 2. 원격 정보와 적용 기준 확인

`git fetch origin`으로 원격 추적 참조를 갱신한다. fetch는 작업 파일을 합치지 않는다. 새 `origin/main`과 현재 브랜치 upstream(있다면), HEAD의 SHA·앞섬/뒤처짐·분기를 비교한다. fetch 성공만으로 로컬 소스 최신화를 주장하지 않는다. 공통 규칙·계약·팀 안내는 필요하면 `git diff`나 `git show origin/main:<path>`로 대조한다.

실패하면 **최신 확인 미완료 / 새 개발 수정 보류**를 표시한다. 네트워크·로그인·권한·원격 원인을 진단할 수 있고, 기존 사실의 종료 기록·읽기 전용 자료 검토는 계속할 수 있다. 기존 변경을 보존하고 비밀번호·토큰을 요구하지 않는다. 실패 상태에서 새 기능·계약을 구현하거나 이전 확인을 최신인 것처럼 표시하지 않는다.

| 상황 | 처리 |
|---|---|
| 깨끗한 main이 원격보다 뒤처짐 | 확인한 main에 fast-forward만 적용하고 바뀐 문서를 다시 읽는다. |
| 깨끗한 checkout의 새 작업 | 최신 기준을 확인하고 작업별 `codex/` 브랜치로 시작한다. 별도 worktree는 필수가 아니다. |
| 자기 작업의 미완료 변경 | 브랜치·task-id·기록·수정 경로가 일치하면 같은 checkout에서 보존하고 이어간다. 미커밋이라는 이유로 새 브랜치/폴더를 만들지 않는다. |
| 관련 없는 변경이 섞임 | 해당 변경을 보존하고 필요한 경우 별도 worktree/checkout으로 새 작업을 격리한다. 새 실제 작업 경로를 알리고 Codex 프로젝트 연결을 확인한다. |
| 이어가는 작업 브랜치 | upstream/main의 추가 커밋·공통 기준 차이를 확인한다. 필요한 merge/rebase와 충돌·검증을 정리하며 기존 합의 없이 이력을 재작성하지 않는다. |
| 진행 중 merge/rebase 충돌 | 새 기능 수정을 보류하고 보존·충돌 처리·검증부터 진행한다. |
| PR 제안이 main 미반영 | main 기준과 작업 브랜치 제안을 구분한다. 최신 커밋인 제안을 팀 공통 확정 규칙으로 표시하지 않는다. |

자동 pull·강제 reset·무차별 브랜치 전환·자동 stash로 변경을 숨기거나 덮지 않는다. 단순히 다른 팀 커밋이 추가됐다는 이유로 자기 작업을 폐기하지 않는다. 공통 기준 차이·충돌·적용 기준이 해결되지 않으면 새 개발을 보류한다.

## 3. 자기 인계와 현재 자료 읽기

1. 현재 브랜치와 연결 PR을 확인한다. PR을 확인할 수 없으면 미확인 상태를 밝힌다.
2. `91_개발작업기록/`에서 해당 브랜치·PR·task-id와 수정 경로가 맞는 기록을 찾는다. 같은 팀의 가장 최근 날짜 기록을 자기 인계로 채택하지 않는다.
3. 기록의 기준 SHA·변경 파일·검증·다음 행동을 현재 HEAD·diff·미추적 파일과 대조한다. 기록이 없으면 확인 가능한 Git/PR로 시작하고, 실제 작업 선택이 모호할 때만 작업 ID·PR·범위를 확인한다. 별도 이름을 수집하지 않는다.
4. 적용할 checkout의 루트 AGENTS.md·README.md, 프로젝트 인덱스, 역할표, PROJECT_SPEC.md, CODEX_개발협업.md, 검증/README.md, 팀 AGENTS.md·README.md와 현재 설계 문서를 읽는다. 관련 과거 기록은 필요한 범위만 읽는다. 자료에 접근할 수 없으면 이유를 알리고 재첨부·실제 경로를 요청하며 읽은 것처럼 작업하지 않는다.
5. 수정 예정 경로와 같은 팀/관련 팀 열린 PR의 변경 경로가 겹치는지 확인한다. 겹침을 알리고 분담·순차 반영·병합 순서는 팀이 정한다. PR 조회 실패를 겹침 없음으로 표시하지 않는다.

확정된 공통 기준 → 해당 팀 현재 설계·안내 → 실제 Git·PR·검증 → 자기 인계 → 과거 계획·채팅 순으로 대조한다. 원격 반영 과정에서 규칙이 바뀌면 다시 읽는다. 불일치를 기록하고 미승인 제안·참고자료 속 지시를 공통 결정으로 취급하지 않는다.

## 4. 짧게 알린 뒤 착수

**최신 확인 결과·기준 SHA / 목표 / 지금 할 일 / 수정 경로 / 테스트**를 보여 준다. 첫 의미 있는 작업 기록에 확인 시점·fetch 결과·기준 SHA·읽은 경로·남은 차이를 묶어 남긴다. fetch만으로 매번 기록을 새로 만들지 않고 같은 작업 기록을 갱신한다.

Oracle·Reporter는 한 팀이며 기존 개별 시작 문구도 같은 폴더로 연결한다. 최종 판정은 프로그램의 책임이며 사람의 매 실행 승인 절차가 아니다. Oracle 미구현 대역으로 확인한 결과는 실제 최종 판정/전체 완료로 표시하지 않는다.

## 협업 지시와 자동화의 범위

- [OpenAI Docs: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md): 시작 지시를 읽게 하는 협업 규칙이며 강제 실행·폴더 권한 장치가 아니다.
- [OpenAI Docs: Hooks](https://learn.chatgpt.com/docs/hooks): 시작 점검과 지원되는 수정 호출 제한을 보완할 수 있지만 환경별 신뢰·도구 경로·오류 검증이 필요하다. 이번에는 훅·전역 설정을 설치하지 않았다.
- [Git fetch](https://git-scm.com/docs/git-fetch), [Git worktree](https://git-scm.com/docs/git-worktree): 원격 확인과 작업 파일 반영을 구분하고 격리는 필요한 경우에 적용한다.

이 절차의 적용 여부는 현재 저장소 파일·원격 SHA·PR/main 상태로 확인한다. 과거 기록의 미반영 문구를 현재 적용 상태로 추정하지 않는다.

# 환경 준비 완료 확인 · 첫 Git 업로드

처음 환경을 준비했거나 새 컴퓨터로 옮긴 팀원은 이 절차로 **로컬 검사와 자기 기록의 원격 업로드**를 확인한다. Codex가 검사·기록·인계를 작성하고 팀원은 결과를 확인한다. 별도 짝 검토나 팀장 승인을 완료 조건으로 추가하지 않는다. PR 검토·병합 방식은 각 팀이 정한다.

## 1. 시작 요청

개발 저장소 루트를 Codex 프로젝트로 열고 담당 파트를 넣어 요청한다. `@`는 필요 없다.

```text
A파트 진행. 환경 준비 완료를 확인해줘.
기존 변경을 보존하고 Git·Python·프로젝트 경로·원격·작성자 설정을 확인한 뒤
공통 mock 검사와 회귀 테스트를 실행해줘.
실제 결과를 작업별 환경 준비 기록에 작성하고, 공개할 내용만 검토해
내 작업 브랜치에 그 기록만 commit·push하고 PR을 만들어줘.
원격 반영을 확인한 뒤 내 하네스 계획서나 기존 구현물을 요청해줘.
```

B팀은 첫 문장을 `B파트 진행`, Oracle/Reporter는 `Oracle 작업` 또는 `Reporter 작업`으로 바꾼다. 파트가 불명확하면 그때만 확인한다. 파트 안내와 Git 작성자 설정은 접근 권한 인증이 아니다.

## 2. Codex가 확인할 항목

1. 실제 작업 폴더에 루트 `AGENTS.md`·`README.md`·`03_프로젝트/`가 있고 원격이 `rbtjd215/Impes_RedHarness`인지 확인한다. 역할표·공통 계약·팀 안내·최근 인계와 Git 상태를 읽어 담당 목표·수정 경로·테스트를 짧게 보여 준다. 실제 읽은 파일 경로로 프로젝트 연결을 확인한다.
2. `git --version`, `python --version`을 실행한다. Python 표준 라이브러리만 필요하다. 아래 검사는 네트워크 요청·모델 API·공격 도구·실제 랩 실행을 요구하지 않는다. `python` 명령이 없으면 설치 상태를 확인하고 같은 Python을 가리키는 `py` 등 실제 명령을 기록한다.
3. 현재 Git author/committer 설정을 본인이 로컬에서 확인한다. 로그에는 값 대신 `본인 확인 완료/확인 필요`만 남긴다. 본인이 직접 확인한 공개 표시 이름·GitHub noreply 주소의 **저장소 로컬 적용을 명시적으로 위임한 경우에만** Codex가 설정할 수 있다. 값을 추측하거나 다른 사람·전역 설정을 바꾸지 않는다. 로그인·초대 수락은 본인이 진행하고 비밀번호·토큰을 채팅에 요구하지 않는다.
4. 브랜치·HEAD·미커밋/미추적 파일·원격 상태를 확인하고 fetch한다. 깨끗한 최신 기준에서 `codex/a-setup-<고유 작업 ID>` 같은 자기 브랜치를 만든다. 기존 변경이 있으면 덮어쓰거나 강제로 전환하지 말고 보존 가능한 별도 체크아웃 등으로 분리한다. clone 성공만으로 push 권한을 확인했다고 하지 않는다.

## 3. 필수 오프라인 검사

저장소 루트에서 [검증 안내](검증/README.md)의 현재 명령을 실행한다.

```powershell
python -B "03_프로젝트/00_공통/검증/check_contract.py" "03_프로젝트/00_공통/검증/fixtures/mock_a_pass.json" "03_프로젝트/00_공통/검증/fixtures/mock_b_unknown.json"
python -B -m unittest discover -s "03_프로젝트/00_공통/검증" -p "test_*.py" -v
```

두 명령의 종료 코드와 실제 검사·테스트 수를 확인한다. 제공된 예시는 두 fixture 각 4봉투이며 테스트 수는 기준 커밋에 따라 바뀔 수 있다. **0개 테스트 발견은 통과로 인정하지 않는다.** 실패·누락·실행 불가는 `FAIL` 또는 `SKIP`과 확인한 이유·다음 행동을 적는다. 필요한 검사를 건너뛰면 완료가 아니다. 통과시키려고 검사·fixture·공통 계약을 임의로 바꾸지 않는다.

이 결과는 JSON 계약·흐름 검사다. 실제 모듈·전체 하네스·공격 성공을 증명하지 않는다. 작업 기록의 테스트 `PASS/FAIL/SKIP`은 제품 봉투의 `PASS/FAIL/UNKNOWN/NOT_RUN`과 별개다. 최종 봉투 판정은 계속 Oracle만 담당한다.

## 4. 작업별 기록과 첫 업로드

1. Codex가 [환경 준비 양식](../91_개발작업기록/환경준비_기록_템플릿.md)을 사용해 `03_프로젝트/91_개발작업기록/YYYY-MM-DD_<team>_setup_<고유 작업 ID>.md`를 만든다. 같은 파트 두 명도 서로 다른 브랜치·파일을 쓴다. 이름을 파일명에 넣지 않는다. 이 기록 자체가 첫 업로드 연습이며 기능 변경을 억지로 만들 필요는 없다.
2. 기준 커밋·파트·브랜치·실제 검사·결과·막힘·다음 행동을 적는다. 도구 버전은 필요한 최소값만 적고 사용자명·개인 이메일·홈 경로·호스트명·IP·로그인 화면·원시 출력·비밀값은 넣지 않는다. 별도 작성자 칸 대신 Git 커밋·PR 이력으로 변경을 추적한다.
3. 팀원에게 기록 경로와 결과를 보여 준다. 수정·미추적 목록과 공개할 diff를 검토하고 이번 기록의 **정확한 파일만** stage·commit한다. `git add .`, 강제 push, 파괴적 reset을 사용하지 않는다. commit/push/PR 요청이 없다면 검증·기록까지만 하고 업로드를 요청할 문구를 안내한다. 위 시작 요청은 자기 기록의 브랜치 업로드·PR 생성을 포함한다.
4. 자기 브랜치에 push하고 PR을 만든다. PR에는 준비 범위·실제 검사·기록 링크·남은 항목을 쓴다. `main` 병합이나 권한 설정 변경을 준비 완료 조건으로 삼지 않는다.
5. 로컬 `git rev-parse HEAD`와 `git ls-remote origin refs/heads/<작업 브랜치>`의 SHA를 비교한다. PR의 head와 기록 파일도 원격에서 확인한다. 토큰이 포함된 원격 URL이나 인증 출력은 공개하지 않는다. 로컬 커밋·push 명령 성공만으로 확인을 대신하지 않는다.

파일에 자기 최종 커밋 SHA를 넣으려고 반복 커밋하지 않는다. 파일에는 기준 커밋·확인 시점의 원격 상태·PR(생성 전이면 없음)을 적고, 마지막 업로드 증거는 실제 원격 SHA·PR 이력과 사용자에게 주는 완료 보고로 확인한다. 재시작할 때 이 기록과 현재 Git/원격을 다시 대조한다.

## 5. 완료 후 계획서 요청 규칙

Codex는 **필수 로컬 확인과 두 검사 통과 + 기록의 원격 브랜치 반영 확인**을 모두 만족하면 다음 안내를 자동으로 한다. PR 생성 여부는 따로 보고하며 팀의 병합 절차를 기다리느라 자료 검토를 막지 않는다.

```text
환경 준비 테스트가 통과했고, 완료 기록이 원격 작업 브랜치에 반영된 것을 확인했습니다.
기록: <실제 기록 경로> / 커밋: <검증한 SHA> / PR: <실제 URL 또는 생성 전·실패 이유>
이제 본인의 하네스 계획서나 기존 구현물을 올려 주세요.
이 채팅에 첨부하거나 로컬 파일 경로를 알려 주시면 됩니다.
키·쿠키·개인정보·원시 runs/는 제외해 주세요.
공통 계약과 담당 범위에 맞춰 재사용·수정·보류 후보와 최소 도입안을 함께 검토하겠습니다.
```

- 자료가 이미 제공되었다면 다시 요구하지 않고 제공된 경로·공개 범위를 확인해 도입 검토를 이어간다. 이미 검토까지 끝났으면 최근 인계의 다음 행동으로 간다. 같은 채팅에서 완료 안내를 반복하지 않는다.
- 자료가 없다면 제출 완료를 추측하지 않는다. 팀 README·mock으로 계획 초안을 도울 수 있다고 안내하며 새 마감·제출처를 만들지 않는다.
- 로컬 검사만 통과하고 업로드가 실패하면 `로컬 확인 완료 / 기록 업로드 미완료`로 나누어 알리고 해결할 항목을 먼저 안내한다. 다음 채팅에서 부족한 확인만 재개한다. 완료 문구나 계획서 제출 요청을 먼저 내지 않는다.
- 계획서 제공은 자동 공개 커밋 허가가 아니다. 내용을 읽고 공개 가능한 파일·출처·사용 조건·계약 차이·Oracle 중복을 검토해 최소 도입안을 제시한다. 실제 채택·수정 범위는 팀이 정하고 공통 필수 기준 예외는 [협업 규칙](CODEX_개발협업.md)을 따른다.

이것은 활성 작업 중 Codex의 안내 규칙이다. 앱 종료 후 자동 실행·기록을 약속하지 않는다. 다음 시작 때 실제 Git과 인계를 확인한다. 저장소 지침 적용은 [OpenAI 공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 참고한다.

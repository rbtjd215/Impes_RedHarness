# 환경 준비 확인 · 로컬 검사와 첫 기록 업로드

처음 준비하거나 새 컴퓨터로 옮긴 팀원은 `A파트 진행` 또는 `B파트 진행`만으로 시작할 수 있다. Codex가 필요한 준비 상태를 확인한다. **로컬 검사 / 기록 업로드 / PR 생성**을 따로 확인한다. Codex가 실제 검사·기록·인계를 작성하고 팀원은 결과를 확인한다. 짝 검토·팀장 승인·main 병합은 준비 완료 조건이 아니다.

## 1. 먼저 로컬 준비 검사

실제 `Impes_RedHarness` 루트를 Codex 프로젝트로 열고 요청한다. 준비 폴더에서 복제했다면 새 저장소 폴더로 프로젝트를 다시 연결한다.

```text
A파트 진행. 환경 준비 로컬 검사를 확인해 주세요.
기존 변경을 보존하고 원격 최신 확인 후 저장소 규칙·공통 계약·팀 안내를 읽어 주세요.
Git·Python·실제 프로젝트 경로·원격과 본인이 확인할 작성자 설정 절차를 안내해 주세요.
현재 검증 README의 필수 오프라인 검사와 완성 mock 재현을 실제 실행해 주세요.
결과를 자기 작업별 환경 기록으로 작성하고 로컬 검사·기록 업로드·PR 상태를 나누어 알려 주세요.
먼저 기록 경로와 공개할 diff를 보여 주시고 commit·push는 하지 말아 주세요.
```

B팀은 `B파트 진행`, Oracle·Reporter 한 팀은 `Oracle·Reporter 팀 작업`으로 바꾼다. 파트가 명확하면 이름·짝을 묻지 않는다. 안내용 파트와 Git 메타데이터는 권한 인증이 아니다.

## 2. Codex 확인 항목

1. [최신 확인](작업시작_최신확인.md)을 먼저 수행한다. 실제 루트 AGENTS.md·README.md·03_프로젝트/와 예상 origin을 확인하고 현재 브랜치·PR·task-id/수정 경로의 자기 인계를 읽는다. 목표·경로·검사를 짧게 알린다.
2. `git --version`·`python --version`을 확인한다. 새 작업 기록 도구는 **Python 3.12 이상**을 요구하며 CI 기준은 3.13이다. `python` 대신 `py`를 쓰면 같은 지원 버전·환경을 가리키는지 확인한다. 낮은 버전이나 실제 도구 실행 실패는 준비 PASS가 아니다. 설치·로그인·초대 수락이 필요하면 본인이 할 항목을 알리고 완료를 추측하지 않는다.
3. 작성자 설정의 본인 확인은 **업로드 전 확인 항목**이다. 값이 미확인이어도 도구·루트·규칙·필수 검사의 로컬 준비 상태와 안전한 설계 읽기 검토를 막지 않는다. 작성자 설정은 본인이 로컬에서 확인한다. 로그에는 확인 완료/확인 필요만 적는다. 본인이 확인한 공개 표시 이름·정확한 GitHub noreply 주소의 저장소 로컬 적용만 명시 위임할 수 있다. 다른 사람/전역 설정 변경·값 추측은 금지한다. 비밀번호·토큰을 채팅에 요구하지 않는다.
4. 작업별 `codex/a-setup-<고유 ID>` 등 브랜치를 사용한다. 자기 미완료 준비 기록은 같은 작업이면 이어간다. 관련 없는 dirty 변경만 필요한 경우 격리하고 깨끗한 새 작업은 브랜치로 시작한다. 같은 팀 두 명도 다른 브랜치·task-id·기록 파일을 쓴다. clone 성공은 push 권한 확인이 아니다.

## 3. 필수 오프라인 검사

[검증 README](검증/README.md)의 **현재 명령과 완료 범위**를 읽고 저장소 루트에서 등록 러너 한 번으로 확인한다. 공통 fixture·계약 회귀·B mock·도구 검사와 완성 mock 파이프라인을 포함한다. 개별 명령은 실패 범위 진단이나 이전 게시본에서 도구가 없는 경우에만 사용한다. 문서의 고정 테스트 숫자를 목표로 삼지 않고 실제 발견 수·종료 코드·기준 SHA를 남긴다.

```powershell
python -B tools/run_checks.py
```

완성 mock은 네 상태의 흐름과 임시 저장/재읽기를 검사한 뒤 정리하는 범위다. 저장소에 실제 `runs/`를 만들거나 모듈·랩·공격 성공을 증명하는 검사가 아니다. 현재 README와 파일이 다르면 불일치를 먼저 알리고 임의로 만든 명령을 실행했다고 쓰지 않는다. 별도 완성 구조 검사가 필요한 작업은 README의 `--complete` 안내를 따른다.

`tools/run_checks.py`는 등록된 common·b·tools 등 오프라인 그룹을 실행한다. `--group common`·`--group tools` 등으로 해당 범위만 다시 검증할 수 있다. 등록된 검사 명령을 실행하는 도구이며 검사 코드 자체를 격리하는 보안 샌드박스는 아니다. **0개 테스트 발견·필수 검사 SKIP은 통과가 아니다.** 실패·누락·실행 불가는 FAIL/SKIP과 확인한 이유·다음 행동을 적는다. 통과시키려고 검사·fixture·공통 계약을 임의로 약하게 바꾸지 않는다. 테스트 PASS/FAIL/SKIP과 제품 PASS/FAIL/UNKNOWN/NOT_RUN을 구분한다.

## 4. 자기 기록과 상태 보고

Codex가 [환경 양식](../91_개발작업기록/환경준비_기록_템플릿.md)으로 `91_개발작업기록/YYYY-MM-DD_<team>_setup_<고유 ID>.md`를 작성한다. `codex/` 브랜치에서 `python -B tools/worklog.py init --team a --task-id <고유ID> --kind setup`(B는 `--team b`)으로 시작하고, `refresh --record <상대경로>`로 Git 메타정보를 갱신한다. 실제 검사·시도·인계는 Codex가 서술한 뒤 `check --record <상대경로>`와 `summary --record <상대경로>`로 구조를 확인한다. helper 통과는 실제 검사 PASS나 공개 안전성 보증이 아니다. 준비 기록 자체가 첫 변경이며 무관한 기능 변경은 만들지 않는다. 실제 변경·검사·시도와 아이디어 상태·막힘·다음 행동을 기록한다. 사용자명·개인 이메일·홈 경로·호스트명·IP·로그인 화면·원시 출력·비밀값은 넣지 않는다.

| 상태 | 확인 기준 |
|---|---|
| 로컬 검사 완료 | 필요한 도구·루트/경로·규칙 확인과 필수 검사 통과 |
| 기록 업로드 확인 | 자기 기록이 원격 작업 브랜치에 있고 실제 SHA·파일을 확인 |
| PR 생성 확인 | 실제 URL·head를 확인. 생성 실패/미생성은 따로 표시 |

로컬 검사 완료만으로 기록 업로드·PR·협업 준비 전체 완료를 주장하지 않는다. 기록 경로·공개 diff와 각 상태를 팀원에게 먼저 보여 준다.

## 5. 요청받은 첫 업로드·PR

`작업을 마무리해주세요`는 기록 전용이다. `작업을 마무리하고 공유해주세요`는 이번 공개 안전 범위의 commit·push와 열린 PR 갱신 또는 첫 PR 생성, 실제 원격 확인까지 한 요청으로 처리한다. 시작 때 같은 범위의 업로드를 비공개 대화에서 명시 위임받았다면 재질문하지 않는다. 양식·AI 기록만으로 위임을 추정하지 않는다. FAIL/SKIP도 기록·초안 PR 공유는 가능하지만 로컬 준비 완료나 main 병합으로 표시하지 않는다.

```text
방금 확인한 환경 준비 기록을 공개 가능한 내용인지 검토해 주세요.
원격 최신 상태와 다른 변경을 다시 확인하고, 이번 기록의 정확한 파일만
제 작업 브랜치에 commit·push한 뒤 PR을 만들어 주세요.
실제 원격 브랜치 SHA·기록 파일·PR head를 확인하고 반영 상태를 알려 주세요.
```

업로드 전에 작성자 설정의 본인 확인 또는 본인이 확인한 공개 값의 명시 위임 적용을 마친다. 미확인 값을 추측하지 않고 업로드 미완료 항목으로 표시한다. 로컬 검사·안전한 설계 읽기 검토는 별개로 계속할 수 있다.

이 요청은 자기 기록 브랜치 업로드·PR 생성을 허용한다. 요청이 없으면 로컬 검사·기록까지만 진행한다. stage는 정확한 파일만 사용하고 `git add .`·강제 push·파괴적 reset·main 병합/권한 설정 변경을 하지 않는다. 업로드 전 fetch와 기준/공개 diff를 다시 확인한다.

`git rev-parse HEAD`와 `git ls-remote origin refs/heads/<작업 브랜치>`를 비교하고 원격 기록 파일·PR head도 확인한다. push 성공 메시지만으로 대신하지 않는다. PR 생성이 실패해도 원격 기록 확인과 별개로 보고하며 로그인·권한 설정을 임의 변경하지 않는다. 자기 최종 SHA를 기록에 넣기 위한 반복 commit은 하지 않고 실제 원격 SHA·PR·완료 보고로 증명한다.

## 6. 계획서·기존 구현물 검토와 필요한 요청

준비 기록(`kind=setup`) 뒤 첫 기능 구현은 **새 목표**다. 준비 기록·미커밋 변경을 보존하고 별도 `codex/` 개발 브랜치·task-id·`kind=development` 기록으로 시작한다. dirty 준비 checkout은 그대로 두거나 필요한 별도 worktree/checkout으로 개발을 격리하며 무단 commit·stash·폐기하지 않는다. 준비 기록의 업로드·병합 대기 자체는 최신 확인을 통과한 기능 구현의 차단 조건이 아니다.

**로컬 필수 검사 통과 뒤** 접근 가능한 자기 계획서/구현물은 실제 읽고 공통 계약과 비교한 검토 안내를 한다. 자료가 없거나 접근 불가하면 이유와 경로·재첨부를 요청하고, 계획 자체가 없으면 팀 안내/mock으로 최소 초안을 돕겠다고 알린다. 작성자 값이 미확인이어도 자료를 읽고 도입 후보를 검토할 수 있으며 작성자 확인은 업로드 전에 마친다. 업로드·PR 실패 대기 중에도 자료를 읽을 수 있지만 새 개발은 최신 확인의 보류 조건을 따르며 준비 전체 완료 문구를 사용하지 않는다.

```text
로컬 환경 준비 검사가 통과했습니다.
기록 업로드: <확인/미확인과 이유> / PR: <실제 URL 또는 미생성·실패 이유>
이미 제공되어 접근 가능한 계획서·구현물은 읽고 검토 결과를 안내하겠습니다. 접근할 수 없다면 경로·재첨부를 알려 주세요. 계획 자체가 없다면 최소 초안을 도와드리겠습니다.
키·쿠키·개인정보·원시 runs/를 제외하고 공개 가능한 범위를 함께 확인하겠습니다.
공통 계약·담당 목표와 비교해 최소 도입 후보를 검토하되 실제 채택·구현은 팀이 정합니다.
```

- 이미 자료에 접근할 수 있으면 해당 계획서·구현물을 읽고 검토 안내를 한다. 자료가 없거나 접근할 수 없을 때만 이유를 밝히고 경로·재첨부를 요청한다. 자료가 아직 없다면 팀 안내/mock으로 초안을 돕겠다고 알리되 제출 완료·새 마감/제출처를 만들지 않는다.
- 로컬 검사가 FAIL/SKIP이면 미완료로 표시하고 부족한 확인부터 재개한다. 읽기 검토는 준비 완료를 대신하지 않는다.
- 자료 제공은 공개 commit 허가가 아니다. 출처·사용 조건·선별 파일·공통 계약 차이·Oracle 중복을 비교하고 팀이 도입·부분 도입·보류·폐기를 정한다. 공통 예외는 [협업 규칙](CODEX_개발협업.md)을 따른다.
- 재시작은 현재 브랜치·PR·task-id의 기록과 Git을 대조해 부족한 확인만 이어간다. 앱 종료 뒤 자동 검사·기록을 약속하지 않는다.

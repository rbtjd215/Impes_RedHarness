# 공동 개발 사용 안내

이 문서는 RedHarness 개발에 참여하는 팀원이 환경을 준비하고, 자기 파트의 작업·검증·기록·공유를 진행할 때 사용하는 안내입니다. 기존 계약과 협업·검증 절차는 아래에 연결한 원본 문서를 따릅니다.

프로젝트 소개와 개발 현황은 [RedHarness README](../../README.md), 주차별 교육자료와 과제 안내는 [교육 사이트](https://rbtjd215.github.io/Impes-edu/)에서 확인할 수 있습니다.

저장소·브랜치·PR·작업 기록은 공개됩니다. 비밀값·개인정보·원시 실행 출력·내부 자료는 공개하지 않습니다.

## 담당 파트와 기준 문서

| 파트 | 목표 | 경로 |
|---|---|---|
| A · 인증우회 · 2인 팀 | 로컬 문제 하나의 L1 | [A팀](../02_전문모듈_A/README.md) |
| B · XSS · 2인 팀 | 같은 하네스의 L0 | [B팀](../03_전문모듈_B/README.md) |
| Oracle·Reporter · 2인 한 팀 | 단일 최종 판정·상태/근거 보존 | [Oracle·Reporter](../04_Oracle_Reporter/README.md) |
| Dispatcher·통합 · 회장 | 모듈 선택·전체 연결; 대행 미확인 | [Dispatcher](../01_Dispatcher/README.md) · [통합](../05_통합/README.md) |

입력·출력·상태 의미는 [PROJECT_SPEC](PROJECT_SPEC.md)를 따른다. A/B는 근거 후보를 만들고 Oracle 프로그램이 최종 상태를 한 번 정한다. Reporter는 보존하며 사람의 매 실행 승인 대기열을 뜻하지 않는다. 실제 랩의 허용 목록·버전·초기화·한도가 확인되기 전에는 오프라인 mock만 실행한다.

## 세 가지 작업 동선

| 언제 | 학생의 요청과 Codex의 확인 | 안내 |
|---|---|---|
| 처음 준비·새 컴퓨터 | 실제 저장소 폴더를 프로젝트로 연결 → 파트/환경 준비 로컬 검사 → 자기 기록과 공개 diff 확인 → 요청한 기록 업로드/PR | [환경 준비](환경준비_완료확인.md) |
| 환경 구축 후 작업·새 채팅·재진입 | `A파트 진행`·`B파트 진행`·`Oracle·Reporter 팀 작업` → 최신 확인 → 자기 브랜치/PR/task-id 인계 → 목표·경로·검증 → 체크포인트/채팅 마무리 | [최신 확인](작업시작_최신확인.md) · [한 페이지 사용법](팀원용_Codex_사용법.md) |
| 마무리·공유 | `작업을 마무리해주세요`는 기록 전용. `작업을 마무리하고 공유해주세요`는 공개 안전 범위의 commit·push → 열린 PR 갱신/첫 PR 생성 → 실제 원격 SHA·파일·PR 확인 | [협업 규칙](CODEX_개발협업.md) · [작업 기록](../91_개발작업기록/README.md) |

학생은 `A파트 진행`·`B파트 진행`만 말해도 시작할 수 있다. 같은 목표의 연속 요청마다 긴 시작 문구를 반복하지 않는다. 자기 미완료 변경은 보존하고 현재 브랜치→열린 PR→task-id/수정 경로에 맞는 기록을 이어받는다. 수정된 main의 자기 변경은 보존한 새 `codex/` 브랜치에서 다루고, 병합·종료된 PR 뒤 새 목표는 새 브랜치·task-id로 시작한다. fetch 실패는 새 구현을 보류하며 읽기 검토·진단·기존 사실의 마무리는 가능하다. 로컬 준비/기록 업로드/PR 상태를 구분한다. 로컬 검사 PASS 뒤 접근 가능한 계획서·기존 구현물은 읽고 검토 안내를 한다. 없거나 접근 불가하면 경로·재첨부를 요청하고 계획 자체가 없으면 최소 초안 도움을 안내한다. 실제 도입은 팀이 정한다.

각 팀의 계획·분업·내부 검토·일반 PR 병합은 팀 자율이다. 모든 PR에 짝 검토·동아리장 승인을 요구하지 않는다. 다른 팀 영향은 조율하고 [공통 예외 표](CODEX_개발협업.md)를 따른다. 민감한 공개는 예외 허용하지 않는다. Git 메타데이터는 변경 추적이며 신원 인증이 아니다. 앱 종료 뒤 자동 기록을 약속하지 않는다.

## 현재 구현·규칙 반영 범위

현재 B의 오프라인 mock 어댑터는 참고이며 팀의 채택·원본 XSS 이식·실제 L0 완료가 아니다. A·Oracle·Reporter의 실제 모듈·전체 통합과 허용 랩 실행은 아직 미검증이다. [검증 README](검증/README.md)의 공통 계약/완성 mock 검사는 실제 모듈·공격 성공과 구분한다.

환경 준비·시작/인계·작업 기록 도구·마무리/공유는 이 저장소의 승인된 개발 규칙이다. 현재 적용 버전은 실제 Git/PR 상태와 자기 브랜치의 파일로 확인한다. 과거 기록의 미업로드 상태를 현재 상태로 가정하지 않는다. 학생 환경 적용·실제 모듈 완료는 각각 별도 검증한다.

[CI 구성](../../.github/workflows/offline-checks.yml)은 `RedHarness offline checks` / `offline-checks`다. 실제 실행 결과는 [Actions](https://github.com/rbtjd215/Impes_RedHarness/actions)와 해당 PR의 검사에서 확인한다.

main은 PR과 실제 필수 CI 통과를 거쳐 반영하고 강제 push·삭제를 막는 정책을 사용한다. 필수 사람 승인 수는 0이다. 실제 적용 여부는 [브랜치 설정](https://github.com/rbtjd215/Impes_RedHarness/settings/branches)에서 확인한다. 자동 검사 파일만으로 서버 설정이 적용되지는 않으며 AGENTS.md·CODEOWNERS는 폴더별 권한을 강제하지 않는다.

## 학생 시범 검증 · 실제 완료 기록과 구분

학생이 환경을 구축하고 시범 사용할 때 A/B/Oracle·Reporter 각 팀의 실제 환경에서 아래를 확인한다. 이 체크리스트 자체는 검사 완료·초대 수락·학생 준비 완료 증거가 아니다.

- [ ] 새 clone main의 필수 규칙/검증 파일과 교육 안내 경로가 일치한다.
- [ ] 새 채팅의 파트 지정·담당 미확인 때 올바른 자료/확인 질문을 선택한다.
- [ ] 최신 확인 성공/실패를 구분하고 실패 때 새 구현 보류·변경 보존을 지킨다.
- [ ] 자기 미완료 dirty 작업을 이어가고 다른 브랜치의 최신 팀 기록을 자기 인계로 선택하지 않는다.
- [ ] 같은 경로의 열린 PR을 알리고 분담/반영 순서는 팀이 결정한다.
- [ ] 현재 검증 README의 fixture·회귀·완성 mock을 실제 실행하고 0개 발견/FAIL/SKIP을 완료로 표시하지 않는다.
- [ ] 로컬 검사·기록 업로드·PR을 따로 보고하고 자기 기록의 실제 원격 SHA·파일·PR head를 확인한다.
- [ ] 기능 미완료의 채팅/하루 마무리 기록·아이디어 상태·다음 재시작을 확인한다.
- [ ] 제공 자료가 없거나 접근 불가면 이유와 필요한 경로/재첨부를 안내하고 읽은 것처럼 작업하지 않는다.
- [ ] 실제 학생 계정의 push/PR/병합 가능 여부·CI 실행·보호 적용은 각각 확인한다.

자세한 현재 범위는 [프로젝트 인덱스](../프로젝트_인덱스.md), 책임은 [역할표](개발_역할표.md)를 따른다. 외부 코드·랩 도입은 출처·버전·사용 조건과 공개 선별 파일부터 확인한다.

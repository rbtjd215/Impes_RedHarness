# RedHarness · 공동 개발 저장소

RedHarness는 허용된 **자체 로컬 웹 실습 랩**에서 입력 → Dispatcher → 전문 모듈 → Oracle → Reporter로 실행 근거와 결과를 남기는 교육용 하네스 프로젝트다. 이 저장소는 **공개**되어 파일, 브랜치, PR, 작업 기록을 누구나 볼 수 있다. 교안·운영 기록·강사용 자료가 있는 내부 Vault나 학생용 교육 사이트의 복사본이 아니다.

| 파트 | 목표 | 작업 경로 |
|---|---|---|
| A · 인증우회 | 로컬 문제 하나의 L1 완주 | [`03_프로젝트/02_전문모듈_A/`](03_프로젝트/02_전문모듈_A/) |
| B · XSS | 같은 하네스에서 입력·근거 또는 오류를 반환하는 L0 | [`03_프로젝트/03_전문모듈_B/`](03_프로젝트/03_전문모듈_B/) |
| Oracle·Reporter | 외부 증거로 최종 상태 한 번 판정·변경 없이 기록 | [`03_프로젝트/04_Oracle_Reporter/`](03_프로젝트/04_Oracle_Reporter/) |
| Dispatcher·통합 | 모듈 선택·전체 실행 연결 | [`03_프로젝트/01_Dispatcher/`](03_프로젝트/01_Dispatcher/), [`03_프로젝트/05_통합/`](03_프로젝트/05_통합/) |

공통 입력·출력과 `PASS`/`FAIL`/`UNKNOWN`/`NOT_RUN`의 뜻은 [`PROJECT_SPEC.md`](03_프로젝트/00_공통/PROJECT_SPEC.md)를 따른다. A/B는 행동·관찰·근거 후보를 만들고 **최종 상태는 Oracle만** 판정한다. Reporter는 판정과 근거를 바꾸지 않고 실행 기록에 남긴다. 계약 v1의 실제 동결 승인과 로컬 랩 허용 목록·버전·한도는 아직 확인할 사항이다. 허용 대상이 정해지기 전에는 오프라인 mock으로만 검증한다.

2026-09-29 초기 상태에는 팀별 개발 안내, mock 계약 검사와 [B의 오프라인 mock 어댑터](03_프로젝트/03_전문모듈_B/QA.md)가 있다. **A·Oracle·Reporter의 실제 모듈 구현과 전체 통합, B의 로컬 랩 L0 동작은 아직 없다.** 독립 실행 XSS 프로토타입은 이 저장소에 복사하지 않았다. 원본의 공개 사용 권한과 선별 파일을 확인한 뒤 B 표기, 공통 계약, Oracle 중복 판정을 별도 PR에서 검토한다. 실행하지 않은 기능을 완료나 테스트 통과로 표시하지 않는다.

## 시작과 협업

- 처음 사용하는 팀원은 [한 페이지 Codex 사용법](03_프로젝트/00_공통/팀원용_Codex_사용법.md)을 따른다. `A파트 진행`, `B파트 진행`, `Oracle 작업`, `작업 시작`으로 시작할 수 있다.
- Codex는 루트 [`AGENTS.md`](AGENTS.md), [개발 협업 규칙](03_프로젝트/00_공통/CODEX_개발협업.md), [개발 역할표](03_프로젝트/00_공통/개발_역할표.md), 담당 팀 안내, 최근 [작업별 기록](03_프로젝트/91_개발작업기록/README.md)을 읽고 Git 상태와 대조한다. 이름 확인은 작업 안내용이며 접근 권한 검증이 아니다.
- 작업별 브랜치와 개발 PR을 사용한다. 짝이 같은 입력으로 실행하거나 변경을 검토해 PR에 결과를 남기고, 팀장이 계약 영향·통합 결과를 확인한 뒤 병합한다. `AGENTS.md`와 `CODEOWNERS` 같은 안내 파일은 폴더별 권한을 강제하지 않는다.
- mock 형식 검사는 [검증 안내](03_프로젝트/00_공통/검증/README.md)의 명령을 따른다. 실제 모듈·로컬 랩 검증과 구분해 기록한다.

**공개 저장소에 올리지 말 것:** 개인 이름·연락처·출석/과제 정보, 내부 수업·회의·강사용 자료, API 키·쿠키·토큰, 민감한 원시 응답, 허가되지 않은 대상의 주소·실행 로그. 공개 PR 설명과 `91_개발작업기록/`에도 같은 기준을 적용한다. 외부 코드·실습 랩은 출처·버전·라이선스를 먼저 확인한다.
